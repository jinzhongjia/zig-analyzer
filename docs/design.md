# zig-analyzer design goals, performance targets, and acceptance

zig-analyzer is a language server (LSP) for Zig 0.17. Current stage: feature-complete and entering large-scale pre-production validation on real projects.

---

## 1. Design goals

1. **Incremental**: a query-based engine (dependency tracking + early cutoff) reuses results across requests; editing only a function body does not invalidate the analysis of other functions.
2. **Error-tolerant**: any input (including half-written code) yields a lossless syntax tree and as much semantic information as possible; results that cannot be inferred are `unknown`, which propagates without reporting errors or guessing.
3. **Semantic correctness first**: generics and type construction use real comptime evaluation, not pattern matching; inside a generic function body without a concrete instance, inference uses the instances from the call sites.
4. **Low latency**: edits are not blocked by read requests, and outdated requests can be canceled.
5. **Diagnostics 100% consistent with the compiler**: diagnostics come only from the official Zig implementation; zig-analyzer's own semantic analysis serves only IDE features and never publishes error diagnostics (see §3 for the definition).
6. **Build integration**: the project model is obtained through the official build system protocol (`zig build --listen=-`), without maintaining a custom build runner; without `build.zig`, it falls back to single-file mode and remains usable.

### Non-goals

- Persisting analysis results to disk (the cold-start budget is already met; see §2).
- Non-LSP features such as a debugger or a test runner.

### Design principles

1. **Everything is a query**: apart from inputs, all derived data are pure-function queries, cached and invalidated by the engine.
2. **Signatures separate from function bodies**: the declaration skeleton (ItemTree) contains no function bodies and is the most important early cutoff point.
3. **Stable IDs**: cache keys do not depend on indices that shift with edits (AstId and relative positions within a member are used instead).
4. **Unknown is a first-class citizen**: any problem in user code is data (`ERROR` nodes, `unknown`), not an error, and is not turned into a diagnostic either.
5. **Reuse the official implementation**: formatting, parse errors, and AstGen use `std.zig` directly; semantic errors are produced by the compiler process.

### 2.3 Known gaps

- **Edit → diagnostics on very large files**: on `Sema.zig`, most of the time goes to reparsing (about 54 ms) and the official AstGen (about 48 ms), about 85 ms with the default configuration; with `diagnostics.inactive_code` enabled, the whole file must also be inferred to compute the inactive code ranges.
- **Keystroke → hover on very large files**: every keystroke requires reparsing and rebuilding ItemTree and FileIndex; on `Sema.zig`, about 100 ms is the lower bound.
- **Save → compiler diagnostics**: the time is spent in the compiler itself; `-fincremental` misses errors in 0.17, so it is not enabled by default.
- **Cold-start find references**: for a declaration referenced from many files, the worst case is 1.9 s (the candidate files exceed the parse cache capacity and are parsed repeatedly); warm p95 is 124 ms.
- **Cold-start goto for `error.Foo`**: when the expected error set does not correspond to a declaration (an inferred error set, `A || B`) or the name has no declaration, file indexes must be built for the whole import closure; on this repository's `src/server/Server.zig`, the first time takes about 0.3 s, after which the file indexes stay resident and the work is not repeated.
- **First full semantic tokens request**: on-demand inference of generic instances and heterogeneous loops still has a cold cost, up to 861 ms across the 97 libraries; this value excludes project loading and must not be substituted with the latency of warm requests or small range requests.
- **First comptime-only check of a large type graph**: proving that a type is not comptime-only computes the types of all the fields reachable from it, through pointers as well, as the compiler does; on `Sema.zig`, the first inference that reaches the `Sema` type walks `Zcu`, `Compilation`, and the parts of `std` they hold, parsing about 80 files, which takes about 0.5 s in that request; the results are cached per type afterwards.

## 3. Definition of diagnostic consistency

For **the same disk contents, the same Zig version, and the same build step and build arguments**, the published diagnostics equal the output of `zig build <step>` entry by entry:

- the file and the start and end positions (the ErrorBundle span) are exactly the same;
- the severity and the message text are identical verbatim, and notes and reference traces correspond one to one (mapped to `relatedInformation`);
- nothing extra is reported (generic function bodies that are not analyzed, files not in the compile set, except for the live diagnostics of the files in module directories described below), and nothing is missing (including link errors).

| Source | Trigger | Implementation |
|---|---|---|
| `live` | edit (50 ms debounce) | in-process `std.zig.Ast` + AstGen; falls back to `zig ast-check` when the user's zig version differs from the built-in standard library |
| `compiler` | save | `ErrorBundle` sent back over the build system protocol; `zig build-obj -fno-emit-bin --listen=-` without `build.zig` |

- Live diagnostics are published for the files that can be compiled with a project: the files reachable through `@import` from the root modules of its compile steps (the diagnostics steps and the others, such as tests), the files under the directory of a module's root file (a relative `@import` cannot leave it; files not imported yet get their syntax and AstGen errors while they are written), and the build scripts (`build.zig` and `build.zig.zon` in the root directory, plus the files reachable from `build.zig` through `@import` by relative path, computed from the current text of the files when the project instance starts). Other files under the root directory, outside every module directory, get none. When a file belongs to several projects, they are published as long as one of those projects includes it.
- The official parser and AstGen recurse level by level (about 16 KB of stack per level in Debug builds). An upper bound on the nesting depth is first estimated from the tokens: up to 256, the work runs on the current thread; up to 409600 (102400 on 32-bit platforms), on a dedicated thread whose stack is sized by the estimated depth (at most 8 GiB, 2 GiB on 32-bit platforms; on 64-bit platforms it only takes address space); deeper files get no AstGen and no live diagnostics. The limit is calibrated on common nesting forms (else-if chains, if-expression chains, parentheses, calls, initializers, operator chains): `zig ast-check` (46 MiB main-thread stack) can check up to 102400 levels, and on 64-bit platforms the limit is 4 times that.
- Notes and reference traces are mapped to `relatedInformation`: the reference trace entries come after the notes; an entry with a location points to the referencing site, with the message `referenced by: <name>`; the hidden-count entry is at the start of the error, with the same message as in `zig build`. A note or message that the compiler counts several times ends with ` (N times)`, as in `zig build`. The `@compileLog` output, as `Compile Log Output:` followed by its lines, is appended to the message of the `found compile log statement` error; when the same compilation has other errors but not this one (the compiler then ties the output to no error), it is appended to the first error in a file under the build root (the compiler sorts the standard library and dependencies first), or to the first error when there is none. When unsaved changes hide the error that carries the output, the output is published on its own (severity Information) at the error's start, or at the start of the modified region that hides it.
- Before use, every `ErrorBundle` sent back by a child process (`bsp_step_completed`, `bsp_configuration_failed`, and single-file compile results) has all its indices and strings validated: the message list, each message and its notes at every level, and each source location with the reference trace that follows it lie within `extra`; string indices point to 0-terminated strings; and the counts in hidden markers of reference traces are not treated as strings. Nesting depth and the total amount read are bounded, and self-references and cycles are rejected. When a length given in the header exceeds the message body, the whole message is treated as malformed, and no memory is allocated for that length. An invalid bundle is discarded and logged, and the compilation is treated as having no errors; the generated files and the files read in the same message are used as usual. A path that is not absolute after resolution (on Windows, a path relative to another drive, such as `D:a.zig`) is not treated as a file: in an error bundle, it is treated as no location; in `file_system_inputs`, it is skipped. Numeric values such as lines, columns, and ranges are not validated: a range whose end precedes its start becomes an empty range at the start, and diagnostics that fall out of range after being shifted for edits are not published.
- The origin of a file (`server/origin.zig`) is checked in this order:
  - Fetched dependency packages: packages fetched by hash that contain modules (the `<hash>` subdirectories of the package directory; the package directory defaults to `<build root>/zig-pkg` and changes with `--pkg-dir` and `--system`);
  - Generated files: the global cache and the local cache of each project;
  - User code: files under a workspace root directory, excluding the `.zig-cache` and `zig-pkg` in it (when the Zig installation directory is under a root directory, Zig itself is being developed, so it is user code as well; a root directory inside the Zig installation, such as its `std` opened as a workspace folder, does not count);
  - The Zig installation directory (the standard library, `lib/compiler`, etc.);
  - User code: modules outside the root directories that belong to some project (modules added by path, packages specified with `--fork`).
  - Other files outside the root directories, in no project, are the user's files outside the workspace (opened without a workspace folder, or from outside the folders) once the location of the Zig installation is known; which other files use them is not known.
  - Fetched dependency packages, generated files, and the Zig installation directory are collectively called dependency libraries. The compile context, durability (§4.2), and the scopes of rename (§4.6), server-side watching (§4.8), and workspace symbol are all derived from this one classification.
- The compile context of a file is checked in this order (compile entry points come only from projects and detached files; opening a file does not by itself create a compile entry point):
  - Dependency library;
  - Project: in some project's module graph (the compile set, or reachable from the other compile steps), including modules outside the build root added by path;
  - Project directory: files under a root directory with `build.zig` that are not in the module graph;
  - Unloaded project: `.zig` files with a `build.zig` in an ancestor directory whose project is not loaded (files in another project outside the workspace, or, when the root directory has no `build.zig`, files in projects above or below the root directory). Imports by name can only be resolved by that project's build, so these files are not compiled on their own; as rust-analyzer does for files that belong to no crate, opening one only gives a Hint suggesting that the project directory be added to the workspace. The search through ancestor directories stops at `.zig-cache` and `zig-pkg` (they hold caches and fetched dependency packages, not source code of an enclosing project). The hint is published only after startup has finished and projects have finished their first load, for the same reason that single-file mode defers compiles;
  - Other `.zig` files are detached files, each compiled as a root of its own (single-file mode). With build integration disabled, there are no projects, project directories, or unloaded projects.
  - Paths are only normalized lexically, without resolving symbolic links; prefix comparisons use the same case rules as file identity. File identity folds the case of ASCII letters only on case-insensitive volumes: always on Windows, never on Linux, and on macOS according to each volume (`pathconf(_PC_CASE_SENSITIVE)`, asked once per directory; a path that does not exist follows its nearest existing ancestor), so `Parser.zig` and `parser.zig` on a case-sensitive APFS volume are two files, as they are for the compiler. `zig build` is given the build script by its path under the root directory (`--build-file`): it would otherwise take the build root from its current directory, which the operating system reports with symbolic links resolved, and report the files of the project and of its path dependencies under paths the client does not use.
  - Tools and the client may still spell one file differently: `zig env` locates the Zig installation from the real path of the zig executable (Homebrew's `/opt/homebrew/lib/zig` is reported under its `Cellar`), and FSEvents reports names in the Unicode form stored on disk (decomposed names for the client's composed ones). Two spellings name the same file when their real paths (symbolic links resolved, names as stored on disk) are equal, and the other spelling becomes an alias of the file the server already knows, which keeps its path, origin, and module; only paths the server does not know under that spelling are resolved on disk:
    - A document the client opens under an unknown path whose real path differs is the file at the real path when the server knows that file or it is in a dependency library (the standard library opened through a link keeps the library's origin and module); otherwise the document's own path is used. The origin rules are known only after startup: a library file opened through a link before that remains a file of its own.
    - A path in compiler and build results that the server does not know is the open document with the same real path, if any (the real paths of open documents are cached until a document is opened or closed or a file is created or deleted).
    - Server-side watching: a name in a notification that is not a file of interest is the file of interest in the same directory with the same real path, if any (cached until the files of interest are recomputed or the name is created or deleted).
    - Diagnostics, goto, and hover of such a file use the URI the client opened it with.
  - A file the client opens under several URIs at once (spellings that differ only in case on a case-insensitive volume) is one file, with the text of the document opened or changed last. Each document keeps the client's text of it while several are open: an edit applies to the text of its own document, the file's diagnostics are published to each of its documents, and closing one leaves the file open with the text of another (the closed URI's diagnostics are cleared); the disk contents apply once the last one is closed. Changes to a URI that is not open are ignored.
- Compiler diagnostics come from the latest build of each project that contains the file; single-file compile results are used for dependency libraries, detached files, and other files that belong to no project, but not for files in projects, project directories, or unloaded projects (when a detached file imports them by relative path, they are in a different module, where imports by name differ from those in the project). Multiple results are merged: the text read by the most recent compilation is authoritative; from results with a different text, only non-AstGen errors are taken, shifted according to the diff; of errors with the same range, message and notes (the reference trace is not compared), only one is kept, while errors that differ only in their notes (such as one per inline call site) are all kept. Each note is shifted from the text of its file read by the compilation it comes from to the current text of that file.
- The ranges of compiler diagnostics refer to the text the compiler read; files are read from disk once the build finishes. The compiler gives most locations together with the source line they are on, and a file whose text does not have that line at a reported location changed during the build: its locations are discarded (its errors, and notes and references into it) until a later build reads it again.
- When a file is saved or modified on disk, every project containing it is rebuilt (for a build script, the project is restarted); if the file itself is a detached file, it is recompiled, and so are the roots whose last compilation read it (the compiler's `file_system_inputs`, limited to the directory of the root file) or reported errors in it.
- Single-file mode:
  - Errors in imported files in the results are published on those files (including the standard library), whether they are open or not.
  - Compiles are deferred before startup finishes (the zig environment is ready and projects have started loading) and while some project is still in its first load (before it has read the build graph and computed the compile set): at that point it is not yet known whether files outside the root directories belong to projects.
  - Single-file mode is reconciled whenever the context of files may have changed (the zig environment becomes ready, a project finishes loading, a compile set changes, a new instance replaces an old one, projects or root directories are added or removed, build integration or compiler diagnostics are toggled): roots that are no longer detached files drop their results; deferred compiles are run, and open detached files that have never been compiled are compiled.
  - When a root file is not on disk (it is found deleted when recompiling or closing), its results are dropped.
- With unsaved changes: live diagnostics are based on the buffer; compiler diagnostics are based on the saved contents, with positions shifted by the incremental edits. Lines that differ only in their terminator (`\r\n` or `\n`) count as unchanged.

## 4. Key design points

### 4.1 Layers

```
server/       LSP main loop, scheduling, cancellation, workspace and project management, configuration
ide/          hover · completion · goto · refs · rename · inlay hints · code actions …
ide_db/       reference search · call-site seeds
sema/         InternPool · type inference · comptime interpreter · type rendering
names/        module graph · import / name resolution
hir/          function body IR lowering · local scopes
syntax/       error-tolerant lossless CST · local reparse · ItemTree · AstId · typed AST layer · file indexes (FileIndex, ErrorSets)
diagnostics/  live (official parser + AstGen) · compiler (ErrorBundle) · compile sets
project/      build system protocol client · child-process ErrorBundle validation · zig env · builtin.zig generation
base/         Vfs · URI · inputs · ProjectModel
db/           query engine
util/         helpers shared by all layers: LSP position conversion, structural comparison, memory statistics, logging
lsp/          types generated from metaModel.json · JSON-RPC · transport
```

- Each layer depends only on the layers below it; tests may reference higher layers to drive end-to-end scenarios.
- All queries are registered in `database.zig` to form a single `Db` type. The names layer and the layers above it obtain `Db.Ctx` and the queries of the lower layers through it.

### 4.2 Query engine (`db/`)

- **Red-green verification + early cutoff**: a memo records `verified_at` / `changed_at` and its dependencies; after an input changes, the dependencies are verified one by one, and when a recomputation produces an equal value, the old `changed_at` is kept and nothing downstream is recomputed.
- **Durability**: set according to the file's origin (§3) when file contents are written: high for the Zig installation directory and fetched dependency packages, medium for generated files, and low for everything else; verification skips unchanged levels as a whole. Files that are not written but read from disk on demand during queries (such as the standard library in single-file mode) are low. A memo that passes verification takes the current lowest durability of its dependencies (when an input's durability is lowered but the value stays the same through early cutoff, downstream memos must not keep skipping verification based on the high durability).
- **Incremental computation**: a query may declare `computeIncremental(ctx, key, prev)` to receive the previous value when it is recomputed (used for local reparse).
- **Cycles and depth**: each thread maintains an active query stack, and on a cycle the query's `cycleFallback` is called; when the active query stack is very deep, cycles are detected through an index on the keys, so the cost does not grow quadratically with the depth. When the native stack used by nested computations exceeds a limit, they fall back the same way: the limit is 48 MiB on the server's worker threads (64 MiB stacks; on Windows they are reserved through the executable's stack reserve and committed only as they grow, so a pool worker is charged only for the stack it has used) and 4 MiB on the main thread and other threads. When a top-level read is interrupted this way, the interruption point is first computed from the bottom of the stack and the read is then recomputed, so deep chains complete in segments; each top-level read is segmented at most 16 times, so that even infinite recursion terminates.
  - A result in a cycle is not written to a memo, and its reader does not record it as a dependency either: the dependencies it read are handed directly to the nearest frame on the stack that is not in a cycle. The memo of the cycle's entry therefore depends directly on the queries and inputs read by every member of the cycle, memos form no cycles among themselves, and early cutoff on a member's old memo cannot mask a change seen by the entry.
  - On a stack depth fallback, none of the queries on the stack writes a memo, and dependencies in cycles are no longer passed on to them either, so the fallback in deep recursion keeps a linear cost.
  - During verification, a memo whose dependencies lead through a cycle back to a query on the stack is treated as unverifiable until that query is popped: reading it recomputes it directly, and verifying other memos treats it as changed. Each memo in a cycle is verified only once, so recomputation costs about as much as the first computation.
- **Cancellation**: `pending_write` is the number of write transactions waiting for the exclusive lock; while it is nonzero, read queries return `error.Canceled` on entry to `get`, and canceled computations do not write memos; read requests are answered with `ContentModified`. A write transaction decrements it only after acquiring the lock, so overlapping write transactions do not clear each other's registration. A write transaction may declare the inputs it changes (`beginWriteOf`), and a read transaction the inputs its results may depend on (through its `Mark`): a write cancels only the reads whose inputs it may change (the counters are kept per input as well), and the others finish before it acquires the lock.
- **Concurrent reads**: read transactions run concurrently, and those that need the same memo brought up to date (computed, verified, or restored after eviction) do it once: the first one claims the memo, and the others wait until it releases the claim, then use the memo it wrote, or claim the memo themselves when none was written (its computation was canceled, or its result is in a cycle or cut short by the depth limit). A waiting read is canceled like a running one: a write transaction wakes the waiting reads when it registers, and the cancellation flag of a request is checked every 10 ms. A wait that would close a cycle of read transactions waiting for each other is not taken: such a cycle means that the queries form a cycle across their stacks, and the read computes the memo on its own stack instead, where the cycle falls back as in a single read transaction. Each table has its own lock, taken once per read of a memo that is already up to date.
- **Memory reclamation**: a query may declare `lru` (a count) and `lru_bytes` (a byte count); eviction deletes only the value and keeps the dependencies. The declared values are default capacities, which can be changed with the settings `cache.capacity` (number of syntax trees) and `cache.queries` (count and MB, set per query), corresponding to rust-analyzer's `lru.capacity` and `lru.query.capacities`. `resetQueries` clears the type-related queries a whole generation at a time (together with `InternPool.reset`).
- **Allocator**: release builds use `PagedAllocator`, one heap shared by all threads: cached values are allocated on worker threads but freed on the threads that sweep and run write transactions, so a block freed by any thread must be reusable by any thread. `std.heap.smp_allocator` is not used: its free lists are split by thread slot, so the allocating side cannot get the freed blocks back, and resident memory keeps growing over a session (on the Zig compiler source, 4.5 GB after 720 rounds and still growing). Blocks of up to 32 KiB come from 64 KiB pages carved from 4 MiB segments; a page holds one size class (multiples of 8 up to 64 B, then four classes per power of two, so rounding wastes at most 20% of a block) and has its own free list and count of blocks in use. A size class allocates from the page that most recently got room, so that recently freed blocks, likely still cached, are reused first; but pages with less than an eighth of their blocks in use get new blocks only when no other page has room. After the transient peaks below, about 40% of the pages keep less than an eighth of their blocks, most of them long-lived (the 192 B and 224 B classes hold 40 MB of pages for 2.7 MB of blocks in the long session); sparing them lets the ones whose blocks are freed become empty, which lowers the pages assigned to classes from 0.46 GB to 0.43 GB over rounds 120-240 of the long session at the same session time. Taking each block from the fullest page instead saves 0.01 GB more but reuses cold holes rather than recently freed blocks, which makes allocation-heavy work with 16 threads about 10% slower. A page that becomes empty goes to a pool shared by all size classes, which keeps 256 empty pages committed and returns the others to the system: `madvise(MADV_DONTNEED)` on Linux; on macOS a new mapping replaces the page, since `madvise` leaves the resident size unchanged there; on Windows segments are only reserved, and pages are committed when the pool hands them out and decommitted when it takes them back. On Linux, segments are excluded from transparent huge pages (`MADV_NOHUGEPAGE`): with THP set to `always`, the first touch of a page would back the whole 2 MiB around it, and the first round of the long session would peak at 5.6 GB instead of 2.9 GB. The analyzer's memory has transient peaks of 10-12 GB (the rounds of the long session that compute the largest type graphs), so memory that is never returned, or kept for one size class, would stay near the peak; the cost is that each peak is returned to the system and faulted in again by the next one, which takes system time: the long session takes about 3% longer on macOS (240 rounds) and about 5% longer on Windows (40 rounds), and about 2% less on Linux (240 rounds), where user time drops by more than system time grows. With 40 files requested at once (`BENCH_CONCURRENT=40`), Windows answers about 8% sooner. Each size class has its own lock, and the pool's lock is not held during the system calls that return or commit pages. Larger allocations are mapped directly and returned to the system when freed.
- Only two kinds of errors propagate within the engine, `Canceled` and `OutOfMemory`; query results are self-contained immutable values that store only IDs, never pointers to other memos.

### 4.3 Syntax layer (`syntax/`)

`std.zig.Ast` is not used directly as the IDE syntax tree: its recovery from half-written expressions such as `foo.` is coarse-grained, it does not preserve trivia structure, and its node indices shift globally, which makes local reparse impossible.

- **Red-green tree CST**: hand-written recursive descent that follows the official PEG grammar and never fails; where an error leaves no structure to recover, an `ERROR` node is produced, and concatenating the text of the tree always yields the original source.
- **Local reparse**: when an edit falls inside a brace-balanced `block` / `container_decl`, only that node is reparsed and all other green nodes are reused; the result must be exactly the same as a full parse (ensured by corpus tests and random-edit tests).
- **ZON mode**: the root `source_file` of a `.zon` file (decided by path, `Parse.modeOf`) holds a single expression, parsed as a Zig expression; tokens before it that cannot start an expression (such as doc comments) and extra tokens after it go into `ERROR` nodes. Whether the file stays within the ZON subset is still diagnosed by `zig ast-check --zon`. Reparsing keeps the mode; ZON files are usually small and are always parsed in full.
- **Nesting depth**: neither the parser nor the syntax tree limits the depth; deeply nested code takes full part in name resolution, inference, and every IDE feature. Parsing and the layers that recurse along the tree (HIR lowering, inference, semantic tokens, etc.) are limited only by the thread stack: requests are handled on the worker threads of `Io.Threaded`, whose stacks are 64 MiB. As measured in ReleaseSafe, 35000 levels of nested parentheses, calls, `+` chains, field access chains, `!`, and `?`, and 20000 levels of nested blocks and else-if chains are all handled correctly; in Debug, 5000 levels. Deeper nesting overflows the stack and crashes the process, which the client then restarts. The deepest file in the standard library and `lib/compiler` is 319 levels deep.
  - Responses that return nested structures limit the depth: `std.json.Stringify` panics in builds with safety checks when nesting exceeds 256 levels. Selection ranges keep the innermost 200 levels, and document symbols list only the symbols within 100 levels. Some results echo client values (completion and code action `data`, command arguments, the client's diagnostics), so requests whose params nest more than 128 levels are answered with `InvalidParams`.
- **ItemTree**: the declaration skeleton of a file (names, kinds, flags, signature hashes), without function bodies; when only function bodies change, its value stays the same, so neither the name layer nor signature inference is invalidated. A ZON file has a single member: its root expression (kind `zon`, without a name). It is the BodyOwner that infers the root expression, not a declaration: it takes no part in the outline, symbol search, naming checks, or name resolution (a `.zon` file is not a namespace).
- **AstId**: derived from the parent AstId + kind + name + ordinal among same-named nodes, and stable across edits; nodes inside function bodies are located by their HIR `ExprId`.
- **Position-independent summaries**: `ItemNames` stores a Bloom filter of member names, and `ContainerRels` stores the positions of containers relative to their owner; absolute positions stay in `ItemSummaries` / `FileAstIdMap`, so that merely moving source code does not invalidate semantic search.
- **Typed AST layer** (`ast.zig`): hand-written; it centralizes the knowledge of "which child node holds which information", and its accessors return optionals.
- **Incomplete names**: an unterminated quoted identifier is recovered as a name in syntactic decisions; the CST keeps the original `invalid` token and the diagnostic, and still distinguishes reference, declaration, member, and label positions; HIR lowers a reference that lacks a valid name to an unknown expression, which does not take part in name resolution.
- `std.zig.Ast` is used only for formatting and AstGen diagnostics.

### 4.4 Name layer and HIR (`names/`, `hir/`)

- **Module graph**: comes from the build graph, plus `std` (`std/std.zig` of the compile step's `zig_lib_dir`, or of the zig environment when the step sets none), `builtin` (generated by running `zig --show-builtin` with the module's options in the compilation that reaches it first: options the module does not set are inherited from the module the compiler reaches it from, as the compiler does, and the options of the whole compilation, such as the output mode, `is_test`, the link mode, and libc, come from the compile step; kept in the global cache, found again by the zig version, the native target detected on this host, and the options: options without `-target` describe the host, so a host change such as an OS update generates it again), and `root`. As in the maker's configure program, the `build.zig` of the project and of each dependency package with a `build.zig` (§4.7) is a module of its own, importing the `build.zig` modules of its package's dependencies by the names `build.zig.zon` gives them; the files reachable from it along relative imports belong to it, after the memberships from compile sets.
  - The modules a file belongs to come from the compile sets of the compile steps. A file can belong to several modules (e.g. an exe and a test each create their own module but share the root file); an import by name is looked up in the import tables of these modules in turn.
  - Compile sets follow the `@import`s in the syntax tree, not those recorded in ZIR: a file with a parse error or a duplicate member name has no ZIR, but the files imported through it keep their modules while it is being edited. A relative `@import` that leaves the directory of its module's root file is not followed: the compiler reports `import of file outside module path` and compiles nothing from it.
  - Compile sets are computed when the build graph is read and after each build, and recomputed whenever the imports of a file they reached change (after an edit's debounce, or when the file is opened, closed, or changed on disk), without waiting for a build: a file reached through a new `@import` joins the module at once, also with `diagnostics.compiler` off, when no build runs.
  - When several modules import different targets under the same name, name resolution (members, hover, completion, etc.) uses the highest-priority module: the diagnostics steps come first, native-target ones first among them, and the other compile steps follow in build graph order (changeable with `diagnostics.step`). Position makes no difference: inside a test block, the test module's import of the same name is not used instead. With the cursor on an `@import` or its string, goto (definition / declaration) returns all targets, ordered by the same priority; uses of an alias still jump to the `const x = @import(...)` declaration. A member reached through such an import (`cfg.value`, the field `.fast` of `cfg.Mode`, a type `cfg.Mode`) corresponds to the member at the same path of names in each other target (`Resolver.moduleAlternatives`): goto (definition / declaration / type definition) lists them after it in the same priority order, and the use is a reference of each of them, recorded as ambiguous (renaming it would break the other modules); the files that import a definition in any of their modules are searched for its references. `@import("root")` and `builtin` follow the highest-priority membership. In a test compilation `@import("root")` is the test runner (the default one in the lib directory, or the one the compile step sets), which the compiler makes the root module.
  - Files that belong to no module (single-file mode, files in no compile set, files during project loading) and the build scripts are in a compilation of their own (`ModuleGraph.none`): they import std of the zig environment, their `builtin` is for the native target in Debug mode, and so is their type layout (`build.zig` is compiled for the host by the build runner, and other files by `zig build-obj` without `-target`). `@import("root")` is `unknown`: such a file may be imported by another file through a relative path, or compiled by `zig test` (where the root file is the test runner); values read through `@hasDecl(root, ...)` (`std.options`, etc.) are therefore `unknown` and produce no inactive code, while files in a compile step keep the root of theirs. Navigation (goto, references, rename) takes as its targets the files that may be compiled as the root (`Resolver.singleFileRoots`): the files outside the module graph that reach the file through relative imports and that no such file imports, as single-file mode compiles a file on its own as the root module; `root.marker` goes to `marker` there and is one of its references.
  - **Compilations**: a compilation (`ModuleGraph.Compile`) determines `@import("std")`, `@import("root")`, the `builtin` of the standard library and of each module, and the type layout (the target of its root module's builtin, §4.5); compile steps with the same root, standard library, and builtin are one compilation. Each file has its own compilation (`ModuleGraph.home`): the one that reaches it first in the priority order above, or the compilation of files in no compile step. Code is analyzed in the compilation of the code that reaches it, as the compiler compiles a shared file once per compilation: a Windows exe and the host tool that generates its sources read the standard library with their own `builtin` and `std_options`, `build.zig` reads it with the host's, and two workspace folders never read each other's `root`.
    - The compilation is part of the instance context (`inst`) of the sema queries (`Infer`, `DeclType`, `LocalValue`, `ErrorSetOf`, `CallEval`) and of the identity of the values they produce (container types, function values, inferred error sets, generic instances): where code outside every generic function is analyzed in a compilation other than its file's own, `inst` is a `context` key of the InternPool instead of null, and the instances created there end their `parent` chain with it. It travels like an instance: code of another file reached from compilation C (through `@import`, a member access, a call) takes C, normalized to null when C is that file's own compilation, so a project with one compilation analyzes every file once with the same keys as without compilations. A computation runs entirely in one compilation, as the compiler never mixes them: `enterContext` derives it from the key, the `Resolver` resolves std, builtin, and root in it (`ContextImports`), and value computations use its target.
    - Only the analysis is per compilation: files, syntax trees, HIR, indexes, and every location the IDE features return are the real files, and declarations (`Def`, `OwnerKey`) have no compilation, so references, rename, document highlight, and workspace symbol see each position once. A request in a file analyzes the file in its own compilation; instances found at call sites carry the compilation of their caller.
    - A shared file is analyzed lazily, once per distinct compilation that reaches it, and only for the members that compilation uses; the cost is measured in §2.4.
- **Name resolution**: local scopes → the chain of lexically enclosing containers; `a.b.c` resolves namespaces along `@import`, container definitions, `@This()`, and alias chains. A `.zon` file imported with `@import` is a value (see the semantic layer), not a namespace.
- **HIR**: function bodies, initializer expressions, comptime / test blocks, and field types and default values are all BodyOwners; they are lowered to an error-tolerant expression IR (not ZIR, which is not generated when there are syntax errors), and local scopes are computed at the same time; when a member's source is unchanged, the previous Body is reused. The root expression of a ZON file is a BodyOwner too; `inf` and `nan` in it (decided by the source text of the identifier, as ZonGen does) are lowered to float literals: they are inferred as `comptime_float` and highlighted as numbers.

### 4.5 Semantic layer (`sema/`)

- **InternPool**: the unique representation of types and comptime values; the same Key yields the same Index. When it exceeds `sema.max_intern_pool_mb`, it is reclaimed as a whole generation once no read transaction is in progress (the reclaim changes no result, so it does not cancel requests), after which results are inferred again on demand. The reclaim also waits until the type information is twice the most that one request or diagnostics publish has added: reclaiming what a single request needs would make every later request that needs it infer it all again and exceed the limit once more (call-site seeding over a project whose tests instantiate generic code with hundreds of types needs about 650,000 keys for one request). Integers in the comptime interpreter are not interned until a result is handed out, so the intermediate values of comptime loops do not bloat the InternPool. Calls whose arguments contain such integers do not go through `CallEval`; they execute in a new interpreter (with its own memory and backward branch count, as with `CallEval`), and their results are cached within the current evaluation by instance, quota, and arguments (the number of entries is bounded, and the cache is cleared when full). Once half of the native stack is used, these calls go through `CallEval` instead, so very deep recursion is still computed in segments by the query engine. The identity of a container type does not depend on its field types, so recursive types do not form cycles.
  - Error sets with the same members are the same type whatever the order of their names; the set keeps the order of the first set interned with those members, which `@typeInfo(E).error_set.error_names` lists (the compiler lists the names in the order it first saw them, in practice the declaration order), while type names sort them by bytes as the compiler does.
  - Pointer types keep their attributes as the compiler does: `align` (an explicit alignment equal to the natural one still makes a different type: `*align(4) u32` is not `*u32`), the host size and bit offset of a bit pointer (a bit range covering the whole child is dropped), `addrspace`, `volatile`, and `allowzero` (implied for C pointers). An attribute whose expression cannot be evaluated is unknown, so the type is never known to equal another and is shown as `align(unknown)`; where a condition cannot be evaluated, branches giving pointer types that differ only in their alignment give that pointer type with an unknown alignment (`if (alignment) |a| []align(a) T else []T` in a generic body).
    - `&x` takes the attributes of the place: the `align(...)` of a variable, and for a field or element those of the pointer it is reached through adjusted as by the compiler's `fieldPtrType` / `elemPtrType` (a field of a packed struct is a bit pointer such as `*align(4:0:4) bool`; a field of an extern struct is aligned by its offset; with an explicit alignment, an element is aligned by its offset).
    - Derived pointers keep the attributes as the compiler gives them: slicing (`s[a..b]`, also the `*[N]T` of comptime-known bounds) and pointer arithmetic (`p + n`, `p - n`) take those of a pointer to the start element (`[]align(16) u32` sliced from 1 is `[]align(4) u32`; slicing from a nonzero index drops `allowzero`); `.ptr` keeps them; pointer captures of `for` point to an element at a runtime index (an `inline for` capture whose first element is aligned differently from the others has an unknown alignment), those of `if` / `while` / `switch` to the payload or union field as `&x` does (a pointer to an error union payload keeps only the address space); peers of pointers take the lower alignment (explicit unless neither side's is), and `volatile` / `allowzero` when either side has them, and do not resolve when the address spaces or bit ranges differ.
  - Function types keep their calling convention and whether they are generic (comptime or `anytype` parameters), as in the compiler: a declaration without `callconv(...)` is `.c` when `export` or `extern`, `.@"inline"` when `inline`, and `.auto` otherwise. `.c` and the tags without options are known from the syntax; another value of `std.builtin.CallingConvention` is evaluated, and when it equals the target's C calling convention (`builtin.target.cCallingConvention()`) it is `.c`, as the compiler prints and compares it (`callconv(.{ .x86_64_sysv = .{} })` on x86_64-linux); when it or the C calling convention cannot be evaluated, the calling convention is unknown (`callconv(unknown)`, never known to equal another). Types print `callconv(...)` as the compiler does (`fn (u8) callconv(.c) void`), `@typeInfo(...).@"fn"` fills `attrs.callconv` (the value of `.c` needs the target) and `is_generic`, and `@Fn` reads the calling convention back.
- **Core queries**: `DeclType` (the type and comptime value of a declaration; reads only the signature), `Infer` (BodyOwner + instance → the type and resolution target of every expression), `CallEval` (comptime calls, memoized per instance and arguments), `ErrorSetOf` (inferred error sets), `LocalValue` (a single local binding).
- **Inference**: bidirectional inference mirrors Zig's result type semantics, with expected types pushed down from parameters, return values, annotations, and field initializers. Where branches merge, peer type resolution applies (including enum literals with enums, and `&.{}` with slices), and an enum literal in a branch, a `break` value or a loop `else` value without a result type is resolved against the peer type (`if (t) |x| x.kind else .invalid`, `break :blk .b`); `unknown` absorbs everything. To decide whether a call is generic, the call site reads only the callee's parameter forms (`ParamForms`), so callers are not re-inferred when only the callee's function body changes.
  - For an enum literal received by an anytype parameter, the type it is coerced to in the callee's instance (for each parameter, the first coercion in the function body) is recorded in the inference result, and the literal at the call site refers to a member of that type: `testing.expectEqual(.x, actual)` coerces it to the type of actual through `@TypeOf(expected, actual)`.
  - The capture of an `inline` prong on a tagged union is inferred per payload, like a loop over types: each item (for `inline else`, each field not named by another prong) is instantiated separately, so `inline .a, .b => |x|` has the type of `a`'s payload in one iteration and of `b`'s in the other, and is unknown without an iteration when they differ. When a switch operand is comptime-known, the capture of the prong that executes takes the actual payload value, and its type when the capture's type is unknown.
- **`.zon` values**: `@import` of a `.zon` file yields the value in that file (`ZonValue`, cached per file), in inference and in the interpreter alike. The text is processed by the official parser and ZonGen; when it has errors, the value is `unknown`, without guessing at half-edited content. Without a result type, values are the same as in the compiler: struct literals are anonymous structs and array literals are tuples (all of their fields are comptime fields), integers and characters are `comptime_int`, floats are `comptime_float`, and strings are `*const [n:0]u8`; member completion, hover, and member access therefore behave as for the same anonymous literals in source code. `inf` and `nan` need a result type, so values containing them are `unknown`; values nest at most 256 levels deep, and deeper ones are `unknown`. With a result type, the compiler parses the text according to the result type: scalars (bool, null, integers, floats, enum literals) are coerced to the result type, and anything else takes only the result type, with the value `unknown` (strings, tuples, and structs can be parsed as slices, arrays, pointers, or structs with default values, which cannot be obtained by coercing the anonymous value).
- **Result types of `.zon` files**: when a `.zon` file is edited, its root expression is inferred with the result type of its import sites (`ZonResultType`, cached per file and computed when the root expression of a `.zon` file is inferred and when deciding whether `build.zig.zon` uses its schema). Inferring an `@import` records the reachable `.zon` import sites that have a result type (`Result.zon_imports`); the query finds the files that import the file directly through the `FileIndex.imports` of the files in the module graph and of the user's source files under the root directories (detached files and build scripts included) and `resolveImport` (paths ending in `.zig` are skipped), and reads the inference results of the members in them that contain these `@import` calls. Import sites without a result type do not constrain the value and are not counted; when all the other import sites have the same type, free of abstract parameters and unknown parts, that type is used; types that differ only in the optionals and single-item pointers around the value (`T`, `*const T`, `?T`) parse the value the same way, and the type of the value is used. When the types differ, depend on a generic parameter, or there is no such import site, there is no result type, without guessing. Values are converted to the result type as the compiler (`LowerZon`) does: the value of a single-item pointer is parsed as the pointee type and the value of a slice is an array literal (`.{ a, b }` is inferred as `[2]T`), where a `.zig` file needs `&`. Completion of initializer fields and enum literals, goto and references of field names, and inlay hints of field types are therefore the same as for the same typed literal in a `.zig` file; reference search does not skip a `.zon` file with a result type for not importing the file that contains the definition, and skips one without a result type, where nothing refers to a declaration. The dependency chain is inference of the `.zon` root → `ZonResultType` → inference of the importers → `ZonValue`, which reads only the text, so there is no cycle.
- **comptime interpreter**: executes on HIR and supports arithmetic (wrapping / saturating / overflow-checked by bit width), control flow, function calls, container construction, `@typeInfo`, and type-constructing builtins such as `@Struct` / `@Enum`; runtime values and extern functions evaluate to `unknown`. std's generic containers, `std.meta`, and so on therefore need no special-casing. Constructed types (`@Struct` / `@Enum` / `@Union`) are named after the function instance that constructs them (`FieldEnum(S)`); a type that is not constructed in a function and is exactly the value of some constant is named after that constant.
  - Goto for members of constructed types (field access `x.name`, `E.name`, enum literal `.name`, field names in initializers `.{ .name = v }`): the name is a string computed at comptime. When it comes from a string literal (such as the field names zig-clap obtains by parsing help text), the name is evaluated again while tracking the origin of literals: string literals are placed in separate storage cells, and slices keep referencing them, which gives the position of the name in the literal; the candidates are the constants whose initializer contains this literal, and the local bindings of the members containing the use site and the construction site. A single byte taken from a string (short parameter names built with `@as(*const [1]u8, &str[i])`) records its offset in the literal, and a single-character name is also matched by byte. When the literal is not in a constant visible at the construction site but is passed in as an argument (as with `help` in `clap.parseParamsComptime(help)`, which is defined in another file on the caller's side), the argument is traced back through the call sites of the instance: when the argument is a parameter of the enclosing function, the trace continues up to the call sites of the enclosing instance; when the argument is a constant, the constant's initializer is used. When the name comes from `@typeInfo(X)` (`@typeInfo(Tag).@"enum".field_names`), goto jumps to the member of X with the same name. When the name cannot be traced to characters in a literal (such as short parameter names built from the character literal `'h'`), goto jumps to the call that constructs the type (`@Struct(...)`, etc.); `tools/lsp_bench.zig` counts such jumps separately as "at construction", not as mismatches. Fields of anonymous struct values (`anon.first`) are defined by the initializer that creates the value: goto follows the value back through constants without a type annotation, fields of anonymous values, and the items of a tuple a `for` loop iterates, to the field names in those initializers.
  - Builtins: integer arithmetic (including operations with an overflow bit, exact shifts, `@byteSwap` / `@bitReverse`) and float arithmetic, `@memcpy` / `@memset` / `@memmove`, `@call`, and `@embedFile` (relative to the containing file; reads the open document or the disk; `unknown` if the file does not exist). `@src()` gives only its type: the `module` field is the name the build system gives the module, which the project model does not have. Builtins that are meaningful only at runtime (atomic operations, C varargs, return addresses, etc.) and `@intFromError` (whose numbers are assigned by the compiler) cannot be evaluated.
  - As in the compiler, backward branches (each loop iteration, each call) are counted, with a default quota of 1000 that `@setEvalBranchQuota` raises; when the quota is exceeded, the compiler reports an error, while here evaluation gives up. For comptime calls (`CallEval`), counting restarts with the current quota at the call site, and evaluations that inference and goto start directly in a member use the largest quota set by `@setEvalBranchQuota` in the member body: neither gives up before the compiler does.
  - The memory limit is 1 GB (the same as the limit of rust-analyzer's const evaluation), and the number of elements of an aggregate is bounded only by it: before an aggregate is expanded (copying, concatenation, slicing, `@splat`, etc.), the used capacity plus the new allocation is checked; otherwise it is checked once every 256 expressions.
  - comptime-only types (calls that return them are executed at comptime) are cached per type (`ComptimeOnly`); the check covers all fields of structs (files included) and unions (excluding comptime fields) and the types in pointers, arrays, optionals, error unions, and tuples; function pointers are runtime values. Recursive types take the least fixpoint.
  - A slice pointing into local storage is represented as "storage cell + path + range"; elements and the length are read directly from the original aggregate, without copying the range.
  - Interned values are nested at most 256 levels deep (a self-referencing value becomes `unknown`). Aggregates whose elements are all u8 (including structs, such as a value of `struct { short: ?u8 }`) are represented as bytes; elements are read with the declared element type, and anything other than a string is displayed as an aggregate.
  - In inference, slicing and dereferencing a constant (`longest[0..longest.len].*`), as well as `++`, are evaluated by the interpreter when the operands are comptime-known; taking the address of a comptime-known constant yields a pointer to that value (`@field(arguments, &name)`).
  - The value of a `comptime var` is tracked in statement order: assignments and compound assignments to the variable itself update it; once it may be modified otherwise (an assignment to a field or element of it, taking its address, a method call on it, a pointer capture of it), its value is unknown from there on. Zig allows modifying it only in comptime-known control flow; in inference, modifications in if / switch branches whose condition cannot be evaluated, and in loop bodies not inferred per iteration, are treated as unknown (a variable modified by a loop body not inferred per iteration is unknown inside the loop body as well). When a `for` loop is inferred for iteration n, an outer `comptime var` modified by the loop body takes its value at the end of iteration n - 1 (from the inference result of that iteration), and is unknown after the loop.
- **Generic function bodies**: without a concrete instance, they are inferred under an abstract instance (`comptime T: type` is an abstract parameter, shown as `T`; for `comptime x: anytype`, the instance records the argument value; an error union whose error set cannot be evaluated, such as `B.Error!Event`, keeps its payload type, so the result of `try` can still be determined; a container defined in the body, such as `@This()` or `Self` in `fn Pair(comptime A: type, comptime B: type) type`, belongs to the function's abstract instance and is the same type as the call `Pair(A, B)` written there, shown as `Pair(A, B)` with unknown comptime values as `_`, and seeded like any other abstract type); **call-site seeding** infers under a call site that yields a concrete instance, and hover notes the source:
  - Cross-file lookup goes through the file index; when a caller is itself inside a generic function, the caller's instance is taken, and the search for the first instance (hover / goto / completion) goes up at most 16 levels. Call sites are searched in the target's file first, then in the files importing it by import distance, files at the same distance in path order, so the first instance depends only on the source, not on the order in which files were opened
  - All instances (for find references, rename, goto, and the last candidate stage of semantic tokens) are computed as a closure (`AllInstances`): starting from calls outside generic functions, type flow, and dispatch sites in std, it propagates along the calls to the target in each instance of the generic callers until no new instance appears, with no truncation by depth or count. The set of instantiations of code that compiles is finite; when instantiation grows without bound, the closure is truncated and marked incomplete: either argument types nest deeper with each recursion (more than 64 levels of nesting), or the total number of instances exceeds 2^18 (projects with many tests can reach tens of thousands of instances). Rename and naming fixes refuse in that case. The callers of each generic function (`RootCallers`) and a caller's calls under a given instance (`CallsIn`) are cached as queries and shared by the closures of a group of generic functions that call each other. Callers are taken from all files in the project; for a generic function in a file that does not import the target's file, only instances whose arguments lead to types defined in the importers are kept, and scanning its callers takes only callers in the importers and in generic functions
  - Before a caller is inferred, every place where it mentions the function name is first resolved statically (namespaces, global declarations, and parameter types): when all of them refer to other functions, the caller is not inferred (common names such as `print` and `init`). The caller list is cached per target and file (`Callers`) and shared by the lookups at all levels
  - Calls that pass a function value together with an argument tuple (`Thread.spawn(.{}, f, .{ a, b })`, `@call(.auto, f, .{ a })`) use the tuple elements as the arguments
  - Generic methods with no call sites in the project get their instances from dispatch sites in the standard library: in `std.Io.Writer.printValue`, `value.format(w)`, `value.formatNumber(w, ...)`, etc.
  - The results of `@hasDecl` / `@hasField` on abstract parameters are unknown (consistently in inference and the interpreter), so comptime branches that depend on them are not judged inactive; which members a container in an abstract instance (such as `@This()`) has depends only on the source, so the result is still definite; tuples, anonymous structs (`@TypeOf(.{ .tag = "t" })`), and constructed types have no declarations, and their field names are in the type itself; as in the compiler, slices have the fields `ptr` and `len`, arrays the field `len`, and the `_` of a non-exhaustive enum is not a field
  - Instance selection: hover / goto / completion and semantic tokens share a `Refiner` that is reused per owner and picks, for each position, an instance in which the code is active and the target has a concrete type. Candidates are tried in fixed stages: the first instance, the first 32 instances, all instances; they are searched in combination with the iterations of heterogeneous loops, and when none of them yields a type, the error-tolerant result of an active branch is kept. Goto (definition / declaration / type definition) puts the target under that instance first, then lists the targets under every other instance (`AllInstances`, and each iteration of a heterogeneous loop) in which the code is active, each target once: the compiler analyzes each instance separately, and the same member name can refer to a different declaration in each.
  - When a caller is inside a generic function but every place in it that may refer to the target (callee expressions, function arguments passed along with a tuple) already resolves to another function or another value in abstract inference, the caller's instances are not taken: a value already resolved in abstract inference is the same under every instance (unknown comptime conditions select no branch), so another function with the same name (`writer.print`) does not make the lookup go up to the caller's call sites
  - When a caller calls the target through its own comptime type parameter (`P.name(...)`), only the caller's real instances are used: if no call site instantiates the caller with the target's container, no compiler-generated instance exists, so the body stays abstract (unknown), and no instance is pieced together from the target's container
  - The target's container is passed to a generic function as a comptime type argument, which then calls the target through the type parameter (`ctx.get(Q, key)` → … → `Q.compute(ctx, key)` in the query engine): the file containing the dispatch site need not import the target's file, so following the import chain does not find it. Starting from the calls that pass this container type in their arguments, the lookup enters, level by level, the generic calls whose arguments still contain it, until it reaches the call to the target; collecting all instances follows the same path
  - Loops whose loop variable differs in each iteration: iterating over a comptime-known list of types (`inline for`, `for` in comptime; the loop variable is an abstract type), over a comptime-known list of values (`for (params) |param| ParamType(param)`; the loop variable has a type but no value), or over a tuple whose elements have different types (`inline for (.{ &posix, &windows }) |cases|`; the type of the loop variable cannot be determined). When the type of the expression at the cursor cannot be determined, or the call is inside such a loop, inference runs one iteration at a time (over all iterations): the other loop variables of the same loop (`for (types, 0..) |T, i|`) take the value and type of that iteration, and a pointer capture over a constant list (`|*param|`) takes a pointer to the element of that iteration; iterations in which the type at the cursor is noreturn (`.none => continue`) never reach that point and are not chosen. `inline` switch prongs (`inline 0...n => |index|`, where the operand is neither a union nor an error set) are likewise inferred for the value of each prong item, with ranges expanded integer by integer. A container defined in such a loop body or prong body (`const Wrapper = struct { inner: V };`, where `V` depends on the loop variable) takes the instance of that iteration when inferred per iteration (the instance records the loop variable and the iteration number), so its field types can be determined; when not inferred per iteration, it takes an instance whose iteration is undetermined, which does not count as a concrete type, and call-site inference expands each iteration instead; hover notes `inferred from iteration <n> of the loop at <location>`
  - The search cache stores the caller owner, expression identities, and instances, and converts them to absolute positions only at presentation; the import closure and the candidate-name queries are reused across members. Arguments, declarations, imports, and the project configuration are still invalidation dependencies, and edits that only shift positions do not repeat the deep search.
- **Other build configurations**: members that do not exist under the current configuration (code compiled only on other targets, such as `posix.system.EVFILT.READ`, or `settings.cflag.CCTS_OFLOW` on macOS) are looked up in the containers of other configurations: the containers under each configuration are collected along aliases and the branches of comptime-conditional `if` / `switch`; the types of instances are collected along local variables, global variables, call return types, and field types. The candidates are distinct container types, with no limit on their number; aliases and inference chains are followed at most 16 levels deep, so that mutually referencing declarations do not form a cycle.
- **Target-dependent**: parameters that depend on the target are computed for each compilation (`ContextTarget`) from the target (architecture, operating system, ABI, CPU features) parsed from the builtin.zig of its root module, since the compiler lays out every type of a compilation for that target, and results that depend on them are invalidated when the target changes; compilations and modules with the same parameters share one builtin.zig, and each copy is read and parsed only once. A computation selects the parameters of its compilation when it starts (`enterContext`); computations outside every compilation (no module graph yet) use the parts the builtins of all modules and compilations agree on (`TargetAbi`).
  - The parameters include the pointer bit width, the layout rules for vectors, the maximum alignment of integers, the signedness of `c_char`, and the size, alignment, and bit width of the C types and of `f32` / `f64` / `f80` / `f128`, computed by the rules of the compiler's `Type.abiAlignment` / `abiSize`: C types use `std.Target.cType*`, integers use `std.zig.target.intAlignment` / `intByteSize`, and floats follow the C type, the integer that represents them, or compiler-rt's soft-float representation.
  - The bit width of error codes, which sets the layout of error sets and error unions, comes from the compile step's `error_limit` (`--error-limit`; 16 bits by default) as the compiler's `Zcu.errorSetBits` computes it; the common parameters keep it only when every compile step agrees.
  - When the targets differ, those common parameters keep only the parts they agree on: the maximum integer alignment becomes a range, only integers whose alignment it does not affect have a determined layout, and the rest is `unknown`. When builtin.zig cannot be read, the parameters last parsed from it are used (a generated builtin.zig is named by the hash of its contents, so deleting it from the cache during a session does not change them); when it has never been read, only integers of at most 1 byte have a determined layout; without any builtin, the analyzer's own target is used.
  - Values that std does not define are `unknown`: the 32-bit `long double` of AVR, and the C types of ps3 / contiki / managarm.

Document highlight only checks whether its own file reaches the definition, and reports declarations and the targets of assignments (`x = v`, `x += v`, `a, b = v`) as writes and the other occurrences as reads. In files that do not import the file containing the definition, only code in generic functions and the root expression of a `.zon` file that has a result type are checked. Field names in initializers (`.{ .x = v }`) can refer only to fields, so they are not checked when searching for the references of other definitions. While indexing runs, a request first waits (until canceled) for the index of the module graph as it was when the request started, rather than parsing the bulk of the files in one read transaction; it then searches every file of the scope, indexing in the request any file the background pass has not covered, and reads the state at the end of the wait. Symbols in dependency libraries are not listed by default; `workspace_symbol.dependencies` enables them. At most `workspace_symbol.limit` best matches are returned (default 256, 0 for no limit, the same as rust-analyzer's `workspace.symbol.search.limit`), plus every exact name match beyond them (same-named symbols tie, and no longer query could reach the dropped ones): LSP results have no "incomplete" flag; clients that query again as the user types are unaffected, while clients that query only once and filter on the client side (such as Neovim's `vim.lsp.buf.workspace_symbol`) need a higher limit or 0 |

When the file is already formatted with `zig fmt`, the edit is the difference between the original text and the text after the replacement, laid out by `zig fmt` (only lines near the replacement, such as the `;` after a multiline string returning to the statement's indentation, an initializer list changing to one element per line, or lines joined after converting back to a regular string), so the file is `zig fmt` output both before and after the conversion; when the file is not formatted, only the literal is replaced (leaving no trailing whitespace when it moves to the next line), and the layout elsewhere is left untouched. | Naming checks (off by default) | Classified by the declaration's type and comptime value, with results cached per member; the fixes reuse the reference search |

The search scope of find references, rename, the fixes that edit references, and workspace symbol: the project files in the module graph (excluding the standard library), the user's source files under the root directories, and open documents. The root directories are walked for `.zig` and `.zon` files whose origin is user code (§3), without entering hidden directories (`.zig-cache`, `.git`), `zig-pkg`, `zig-out`, or the local caches and package directories of projects, so files in no build graph (single-file mode, build scripts and their helpers, examples) are searched too, opened or not. The walk runs in the background at startup, when root directories are added or removed, and when file events report a source file created that is not known yet, a known one deleted, or a directory created or deleted. Workspace symbol indexes the same files. Until a walk triggered this way has finished, and while a project is in its first load (which files belong to it and what its imports by name resolve to are not known yet), find references, rename, and the fixes that edit references fail with that reason instead of returning partial results; local names and declarations without `pub` (other than fields) are exempt, since only their own file can refer to them.

Rename modifies only the user's own code (by the file origin of §3): definitions in dependency libraries cannot be renamed, and a rename or fix whose references reach into a dependency library (generic code in a fetched package or the standard library that uses a member of the user's type) or a stale copy in `.zig-cache` / `zig-pkg` is refused rather than editing that file: a fetched package is restored from its hash elsewhere, and the Zig installation is shared. In a file outside the workspace folders, only local names and declarations without `pub` (other than fields) can be renamed or lose a parameter, since only that file can refer to them; the files that may use the rest are not known. Declarations that the standard library looks up by name through `@import("root")` (`main`, `panic`, `std_options` and the other `std_options_*`, the Windows and UEFI entry points, `debug` and `os` with the members it reads in them) cannot be renamed in a file that is the root source file of a compilation (the root of a compile step's root module, or a file in no module): std would silently fall back to its defaults or fail to find them, and it is never searched for such uses.

Rename returns no edit, only the reason and its location, in the same cases as the naming fixes (see below): a reference cannot be confirmed (ambiguous in a generic function, a member access of unknown type, incomplete instances, a file with syntax errors that mentions the name), the new name conflicts with an existing one (a member of the same container, shadowing or being shadowed, a reference in the container that would become an ambiguous reference, and finally any new AstGen error in the declaration's file once renamed, such as an ambiguous reference), or the name of a container member appears as a string literal in a file that can access it (`@field`, `@hasDecl`, `@fieldParentPtr`, serialization keys). A tag of an enum constructed from the members of a container through `@typeInfo` (`std.meta.FieldEnum(T)`, as in `list.items(.id)`) refers to the member it is named after, so references list it and rename updates it.

Labels and error names have references, document highlight, and rename too. A label is visible only inside the expression it labels: its references are the label and the `break :l` / `continue :l` that target it (the innermost enclosing block, loop, or switch with the label), and AstGen confirms the renamed file (redefining the label of an enclosing expression is an error). Error names are global: `error.X`, the `X` of `error{ X }`, and `E.X` on an error set type are one error in a compilation, whichever error set they are written in, so their references are searched in the files compiled together with the file at the cursor (the files that reach it through `@import` chains and the files those reach; error set members count as declarations), and a member access `x.X` whose left-hand side is unknown is uncertain. Renaming an error name is refused when a file that is not renamed uses it (the standard library outside its `test` blocks, a file outside the workspace), since its error would no longer be the same, when the new name is already an error name, since the two errors would become one, and when a string literal equals the name (`@errorName` comparisons).

The builtin metadata is pinned to Zig 0.17.0; its provenance, the source archive, and the input file hashes are recorded in `tools/zig/metadata.json`, and the license is kept in the same directory.
`zig build gen` generates `src/ide/builtin_data.zig` offline, verifying the hashes of the official inputs, the compiler version, and the names and parameter counts; at run time only the static table is consulted.
The same step generates `src/ide/manifest_data.zig` (the descriptions of the `build.zig.zon` fields) from `doc/build.zig.zon.md`, verifying the input hash; the set and order of the fields must match the schema exactly.
Of the 128 entries in the compiler's builtin registry, 124 have official documentation; the other 4 explicitly state that the sources do not document them, without inventing signatures or offering bogus signature help.

When a completion item is selected (`completionItem/resolve`), its signature and documentation are provided: functions (functions in scope, members and methods, decl literals, and the functions that function aliases refer to) and auto-import candidates record the declaration they refer to in `data`; `detail` is the signature, and `documentation` holds the doc comment and the location of the definition (for the format, see auto-import below). Function signatures are the same as in hover and signature help (`ast.FnProto.writeSignature`) and are shown as written in the source: comments and parameter doc comments are removed, whitespace is collapsed to a single space, and the trailing comma of a multiline parameter list is not shown; methods of generic instances do not substitute the inferred types. The completion list carries no signatures; a signature is computed only on selection. Constants and variables in scope completion and member completion get only doc comments; a constant whose value is a file (`const x = @import("x.zig");`, a module) also gets the `//!` doc of that file after its own doc comment, the same as in hover.

The kinds of completion items (`CompletionItemKind`) share the classification of `ide_db/symbol_kind.zig` with semantic tokens and are determined by the kind of the declaration and the inferred type: a value that is a type is classified by the type as a namespace (Module, for a file without top-level fields), a struct (Struct, also for a file with top-level fields), an enum (Enum), or another type (Class: unions, opaques, scalars, and so on); a value that is a function (or a function pointer) is Function; a function in a container (not a namespace) whose first parameter is the enclosing container or a single-item pointer to it is Method; a parameter whose value is a type (`comptime T: type`) is TypeParameter; a variable that cannot be modified (const declarations, local constants, captures) is Constant, and the rest are Variable. When the type cannot be computed, the kind of the declaration decides, without guessing from the name. The types of local names come from the inference result of the member at the cursor, inferred inside a generic function body with a call-site instance. Auto-import candidates first take the resident results recorded when the index is built, without parsing the file they are in or inferring the declaration's type: functions (auto-import does not offer methods), consts / vars whose kind the syntax determines (`Decl.form`: literals, a negation, a logical or bitwise not, binary operations other than `orelse` / `catch` / `||`, init expressions, primitive type names and type syntax, merges of error sets, and type annotations; tests ensure the result is the same as classifying by type), consts whose value is a Zig file or a container, and aliases to them; for the rest (function calls, `switch` selecting by target, blocks, and so on), the declaration's type is inferred when the candidate is built, with a cache.

Ordering of name completion: as a name is typed, each candidate's score is its match score multiplied by its source weight, and the server gives `sortText` (the rank) from the highest score to the lowest, keeping the collection order among equal scores. Match scores are computed by `ide_db/fuzzy.zig`, ported from gopls's `internal/fuzzy` (license in `tools/gopls/LICENSE`), with no limit on the lengths of the input and the candidate: the characters of the input appear in the candidate (the whole path) in order, case-insensitively; matches at word starts, consecutive matches, matches in the last segment of the candidate, and matches whose case agrees with the input get bonuses, while skipping the start of the first or the last segment and starting a match in the middle of a word get penalties; when the first character matches in the middle of a word, the first three characters of the input must match consecutively from there, and a match with two or more fragments of fewer than three characters in the middle of words does not count; scores are normalized to (0, 1]. When the input is all lowercase, scoring ignores case, and among equal scores, names whose case agrees with the input come first. Source weights: local names 1.0, parameters 0.98, members of the enclosing container 0.94 (0.02 less per level of outer container, at least 0.86), member paths of local values 0.9, auto-import candidates accessed through a visible name 0.85 (members of namespace aliases, reused direct aliases, private chains in the same file), statement and declaration snippets 0.8, and those that need a new import 0.75; the scores of member paths of local values and of auto-import candidates are also multiplied by a depth factor that drops by 0.05 for each additional segment in the path (to no less than 0.5); candidates whose types fit the expected type at the cursor are further multiplied by 1.25 (see the expected type below). Names in scope are not filtered by the server: those that do not match score 0, sort last, and are filtered by the client.

Member completion after `.` on a value (not a type or a namespace; a single-item pointer is dereferenced once) lists its fields and the functions that can be called on it as methods; those in other files must be pub. Fields are the fields of structs, unions, and tuples, `len` / `ptr` of slices and of single-item pointers to arrays (`ptr` is a many-item pointer with the sentinel of the array), and `len` of arrays; enum and opaque values have no fields (tags are accessed through the type). As the compiler requires, a method's first parameter is the enclosing container `T`, `?T`, `E!T`, or a single-item or C pointer to it (also `?*T`), and a pointer that is not const needs a value that can be modified: a var, what a mutable pointer points to, and the fields, elements, and optional payloads of such values, by the same rule that infers `&x` as `*T` or `*const T`; parameters, constants, value captures, and temporaries (the results of calls) cannot be modified. A first parameter that is `anytype` or whose type cannot be computed counts as receiving the value, and so does a function whose signature cannot be computed.

Member paths of local values: after a non-empty prefix of a plain name expression, the members of the local values visible at the cursor and not shadowed (parameters, local consts / vars, and captures; in enclosing functions, only comptime parameters and the constants whose comptime value the inference result records, since a function in a nested container cannot access the runtime values of the enclosing function, and constants whose value is not recorded, such as struct literals, are not expanded) are candidates too, with the whole path as the label and the inserted text (`gpa` → `sema.gpa`). Values that are types or whose types cannot be computed are not expanded; the types come from the inference result of the member at the cursor, inferred inside a generic function body with a call-site instance.

- First level: the members listed after `.` on the value (see above), dereferencing a single-item pointer once; the path can be modified when it starts at a local var or goes through a mutable pointer.
- Second level: members of fields (`a.b.c`), and members of the results of methods that take only self and return a container (including tuples) or a single-item pointer (`a.b().c`; when a value is returned, the result is a temporary that cannot be modified), to a depth of at most 2. `?T`, `E!T`, pointers to pointers, many-item pointers, methods with parameters, and methods returning `?T` / `E!T` are not expanded.
- The whole path is fuzzy-matched against the input, whether or not its earlier segments match, and only matching paths are returned. Enumerating the second level computes the types of the first-level fields and the result types of the methods that take only self (cached queries); all paths are then scored by name and sorted, and items are built for the matching ones from the highest score down, computing whether a method can be called there, until the limit is reached; together with the auto-import candidates they are subject to `completion.max_auto_imports` (see below).
- Fields have kind Field and carry their types; functions are classified like the same declaration after `.` (Method for a function in a container other than a file that takes that container as its first parameter, otherwise Function) and give their signatures when selected; `filterText` follows the auto-import candidates (see below).

Expected type: as a name is typed, when the name at the cursor has an expected type, the scores of candidates whose types fit it are multiplied by 1.25, which only reorders and never filters; among equal matches, fitting members of the enclosing container (0.94 × 1.25) rank before local names that do not fit.

- The expected type is computed from the parent expression and the inference result of the member at the cursor (with a call-site instance inside a generic function body), without recording anything extra in the inference result: a call argument takes the type of the called function's parameter (a method call through a value skips self, as in signature help: the member is a declaration whose value is a function, including an alias such as `pub const put = putImpl;`; fields of function type do not skip it); `const x: T = ▮` (including declarations in containers and default values of fields) takes the annotated type; `return ▮` takes the return type of the function; `.f = ▮` in an initializer takes the type of the field in the initializer's type (`T` for `?T` and `E!T`); `lhs = ▮` takes the type of the left-hand side; a comparison takes the type of the other side (the tag type for a tagged union; the error set for an error union compared by `==` or `!=`; comptime numbers, enum literals, `null`, and `undefined` have no definite type, nor do types the compiler does not compare: slices, arrays, tuples, and error unions in other comparisons); `@as(T, ▮)` takes `T`; the branches of `if`, `switch`, `orelse`, and `catch`, the value of `break :label`, and `comptime ▮` take the expected type of the expression they produce. Only concrete types count: anytype parameters and parameters that depend on comptime parameters have no expected type.
- It is computed only when the structure can be trusted: not when the statement at the cursor (the innermost item of a block, file, or container that contains the cursor) contains a syntax error, the item before it is an error node, or the call or initializer at the cursor is not closed. Error recovery can produce a wrong structure: after an unclosed call, `x = cd` on the next line is recovered as the arguments `x` and `cd`, from which the type of `x` would be computed. The error of a missing `;` sits at the start of the next token and does not count as an error inside that statement: when the previous statement lacks a `;`, the statement being typed is handled as usual.
- Fitting counts only what can be decided exactly: the same type; `T` when `?T` or `E!T` is expected; an error set, or an error union with the same payload, whose errors are all in `E` when `E!T` is expected (any for `anyerror` and for the inferred error set of `!T`, which `return ▮` expects in such a function); `*T` as `*const T` and `[]T` as `[]const T`; a pointer to an array as a slice or a many-item pointer with the same element type (a string constant as `[]const u8`); for these pointers, the compiler's attribute rules: the alignment may only decrease (an alignment that cannot be computed, such as the natural alignment of a container, does not count), `volatile` and `allowzero` may be added but not removed, and the address space and bit range must be the same; a function as a pointer to it; a type when `type` is expected; functions whose return value fits, and function pointers whose return value fits only when they complete as a call (a function pointer never coerces to its return value). Function types must be the same, including the calling convention: a Zig-callconv function does not fit where a `callconv(.c)` function pointer is expected. Other conversions (integer widening, `comptime_int`, and so on) do not count.
- All returned candidates (names in scope, member paths of local values, auto-import candidates) are checked, and the types of declarations in scope and of auto-import candidates are computed only here (with a cache). The limit truncates by the unboosted scores: the expected type only changes the order of the returned candidates, not which ones are kept.

Snippets are controlled by `completion.snippets` and are on by default; they are used only when the client declares `completionItem.snippetSupport`, and offered only in `.zig` documents. Without them, completion items insert only the name:

- Calls: functions and builtins complete as calls (`add(${1:a}, ${2:b})`), including members, methods, decl literals, function aliases (by the function they refer to), member paths of local values (`sema.fail(${1:src}, …)`, called through a value, so the receiver is skipped), and auto-import candidates. Placeholders are the parameter names, or the parameter type for a parameter that has no name or is `_`; `comptime` and `anytype` parameters get placeholders too; methods called through a value (`x.f`) skip the receiver; with varargs `...`, the last stop is before the closing parenthesis, where the remaining arguments can follow (`printf(${1:format}$2)`). The placeholders of builtins are the parameter names in the official documentation (without `comptime`, `noalias`, and the types); for builtins without documented parameters, the compiler's parameter count decides whether the cursor stops inside the parentheses. With `completion.argument_placeholders` off, only the parentheses are inserted, and the cursor stops inside them when there are parameters.
- Positions that insert only the name: `(` already follows the cursor; the position expects a function value: `&f`, the callee of `@call`, and arguments, fields in initializers, elements of array and tuple initializers, assignment targets, variables, and return values whose type is a function, a single-item pointer to a function, or an optional or error union of them (decided by the syntax of the type annotation or by the computed type), as well as `anytype` parameters that receive a function: another parameter's type is `std.meta.ArgsTuple(@TypeOf(param))`, which accepts only function types (`Io.async(io, function, args)`), or the callee's body (including the functions of containers declared in it) calls the parameter (`param(...)`, `@call(modifier, param, args)`), reads `@typeInfo(@TypeOf(param)).@"fn"`, or passes it on to a parameter that receives a function, followed through every call of the chain, with each parameter looked into once so that recursion ends (`std.Thread.spawn(config, function, args)` passes it to `Impl.spawn`, which passes it to `callFn`, which calls it); the branches of `if`, `switch`, `orelse`, and `catch` and the value of `break :label` take the position of the expression they produce; when completing in scope, declaration names, capture names, and names at the start of a container member. Other `anytype` parameters may receive any value and get calls.
- The placeholders of a function's parameters are cached per function (`CallParams`, keyed by the function's AstId; the values are small and never evicted): computing them parses the function's file, so the first time a function appears (such as an auto-import candidate in a file not parsed since indexing) its file is parsed; the functions listed by completion are spread across many files, which then need not be parsed again after their parse results are evicted.
- Snippets at the start of statements and declarations (kind Snippet, with the inserted text as `detail`): at the start of a statement in a block, `if`, `if else`, `for`, `fori`, `while`, and `switch`, plus `print` and `log err` / `warn` / `info` / `debug` when `std` is the standard library; at the start of a container member, `fn`, `pub fn`, `test`, `struct`, `enum`, `union`, `union tagged`, `error set`, and `import`, plus the imports of `std` and `builtin` when they are not declared yet, `main` at the top level of a file that has no `main` (taking `std.process.Init` as its parameter when `std` is the standard library and has it), and `format` in types that have no `format` (containers that are not opaque, and the file when it has fields), when `std` is the standard library and has `std.Io.Writer`. After `pub`, `pub fn`, `test`, and the `std` / `builtin` imports are not offered, and `main` and `format` lose their leading `pub `; after a doc comment, `test` is not offered; no declarations are offered between fields.
- The ranges replaced by completion items are converted to LSP positions within the line of the cursor (`offsets.Line`), without building a line table for the whole file: every function carries a replaced range, and on large files building the line table is slower than the completion itself. A replaced range runs from the start of the word (or path) at the cursor to its end (for paths, to the end of the string content); when the client declares `completionItem.insertReplaceSupport`, items carry both it and an insert range that ends at the cursor (`InsertReplaceEdit`), so the client's insert or replace mode applies; other clients get the replaced range.
- The cost is the response size: completion after `sema.` in `Sema.zig` lists about 700 items, about 630 of them functions with a snippet and a replaced range, and the response grows from 78 KB to 200 KB; the server's time (including serialization) is unchanged, while the latency of these requests measured by the benchmark client (including parsing the response) is about 2-3 times that without snippets.

Auto-import is controlled by `completion.auto_import` and is on by default:

- Offered only after a non-empty prefix of a plain name expression, never in the context of a declaration name, member name, label, comment, string, or builtin; `enum` members and `union(enum)` tags are container fields without a colon and are likewise excluded as declaration names, while tuple fields of a `struct` (type expressions) can still be auto-imported. For plain identifiers and closed escaped identifiers the whole token is replaced; an unclosed escaped identifier is replaced only up to the cursor, keeping the statements, semicolon, and newline after it.
- `filterText` is kept separate from the inserted expression: for an escaped identifier, the quotes and escape spelling the user has typed are kept as the filter prefix, so that the candidate survives both the plain and the fuzzy matching of native clients.
- When a candidate is selected (`completionItem/resolve`), the signature of the definition it refers to (`detail`, the same as hover), its doc comment, and its location (`documentation`) are provided. The location is the file and line of the definition: for the standard library, the path under `std/`; for a file the current file can import by path, the import path; for other modules, the module name the current file imports it by, plus the path under the module's root directory. The completion item's `data` records the current file, the target file, and the declaration's `AstId`; the signature requires type inference, so it is computed only on selection and not in the completion run on every keystroke.
- Namespace aliases visible at the cursor are reused first (such as `Ast.Node.Index`), without inserting a duplicate import: top-level consts, consts of the containers enclosing the cursor, and local constants in scope in a function or test body (such as `const u = @import("util.zig");`, offering `u.addNumbers`); nested private declarations in the same file can be accessed through a qualified path. A same-named binding in scope takes precedence, and no shadowed binding is generated.
- Direct aliases are reused by canonical declaration identity, covering types, scalar typedefs, functions, and values; when the target is already bound as `Renamed`, filtering by the target name is kept, while the replacement is the existing binding and no import is added. Visible items with the same label merge their filter and replacement metadata, but same-named imports from different sources are not merged; when the alias and the target name share a prefix, `isIncomplete` makes the client query again as typing continues, so that the filter spelling is chosen again.
- Mutable global variables and runtime `extern const` declarations are accessed qualified by their namespace (such as `lib.counter`) instead of copying the stored value into a top-level constant's initializer; `extern const` keeps the read-only completion kind. Before a new top-level binding is added, `BindingNames` is queried: container members (ItemTree), parameters of other functions, local variables, and captures. Member accesses, initializer field names, labels, and type references are not declarations and do not count as conflicts (the current file's name index `FileIndex` is not used as a coarse filter first: when typing character by character, it always has to be recomputed after each edit); when the leaf name conflicts, a namespace binding is used instead, and when the namespace name conflicts too, `@import("...").name` is inserted directly without adding a binding.
- Declarations not offered: methods of structs and other containers (the type of the first parameter is the enclosing container, `@This()`, or a pointer to either, and they are called through an instance), and declarations in files used only by tests, as well as those files themselves. Files used only by tests are computed by `TestOnlyFiles`: reachable via imports from the roots of the modules, but not reachable when following only non-test imports; imports inside test declarations, and imports inside non-pub top-level declarations that production code does not reference but tests do (such as `const World = @import("x_test.zig").World;` used only in tests), are used only for tests, while declarations never referenced at all are dead code and count as production code. When the cursor is in a test declaration or in a file used only by tests, these files are offered as usual.
- Across files, imports follow only chains of public declarations; across modules, the named imports available to the current file are used, and no relative path crossing a module boundary is generated. Modules are offered by their import names (`std`, `builtin`, the named modules, and `root`, the root module of the file's compilation, offered only as a module); a module root is never offered under its file name (such as `root` for a package rooted at `root.zig`). A relative path within the same module must stay inside the subtree of the root directory of the highest-priority module the file belongs to, and the path separator is always `/`. A file in no module (a single-file root, or a build script while the build graph lacks it because build.zig fails to configure) is the root of its own module (except for files of the standard library): the files it reaches through relative imports (outside test code, only through imports not used only by tests) are offered by their paths under its directory.
- New imports are placed by the rules of organize imports (see below): when the block containing the last top-level import declaration is already organized, the import goes to its group and sorted position (a new group gets a blank line before and after it); when the block is not organized, it is not reordered as a side effect, and the import goes after the last import declaration; when there are no imports yet, it goes after the `//!` doc comments and the comment header (such as a license, separated from the code by a blank line) at the top of the file; a comment directly above a declaration stays with it. Same-line comments and regular comments before the doc comments are preserved. When the file starts with a UTF-8 BOM, the BOM stays first and the import is inserted after it. Identifiers and strings are each escaped by their own source rules, and the additional edit does not overlap the main edit.
- Matching: exports at most two segments below the visible namespaces (the namespace aliases visible at the cursor, such as `std` and `const mem = std.mem;`, file imports, and container types) and the module roots (`std`, `builtin`, named modules), kept in `ExportIndex.shallow`, are fuzzy-matched by their whole path: `memeql` matches `std.mem.eql`, and `mem` also offers the members of `std.mem`; deeper exports, private chains in the same file, and declarations in project files are matched by name prefix (ignoring ASCII case). The depth is fixed, with no truncation by time: the result depends only on the source, the input, and the ranking. Names in the index are sorted case-insensitively first and then by bytes on ties, so names that start with the same prefix case-insensitively are contiguous, and exact lookup by name uses the same order.
- `filterText`: the name for candidates whose name starts with the input (ignoring case), and the whole path (`std.mem.eql`) for those matched by path, so that clients that filter only by prefix also keep the candidates matched by name. Whether to filter by case is up to the client (Neovim, for example, follows `ignorecase`/`smartcase`).
- Ranking follows the ordering of name completion above: reusing an existing alias and access through a visible name rank before adding a new import; among equal matches, shallower candidates come first, and so do candidates whose case agrees with the input. The candidates besides the names in scope (auto-import candidates and member paths of local values) total at most `completion.max_auto_imports` items (default 128, 0 for no limit, the same as clangd's `--limit-results`); truncation keeps the highest-scoring ones and uses `CompletionList.isIncomplete` to ask the client to query again as the prefix changes. A short prefix can match over a thousand declarations: only the matching candidates are scored and sorted first, and then labels are built, visibility is checked, and import edits are generated in order until the limit is reached; whether an alias is shadowed is checked only when it is used.
- Before a name is typed in an expression (nothing typed yet, or only a primitive name or `_`), auto-import candidates and member paths of local values are not listed; when either could follow (auto-import is on, or there are local values to expand), the list is marked `isIncomplete` so that the client queries again once a prefix is typed.
- Namespaces and the canonical targets of aliases are evaluated by `Resolver.namespaceOf` / `aliasTarget`, the same implementation that goto, hover, and other features use; when the initializer is in conditional form (`pub const X = if (cond) A else B;`, `switch`), its value is computed by inference, taking the branch selected at comptime:
  - `FileDecls`: the declarations accessible from the file root, derived from the ItemTree (nested under named consts whose value is the container itself), and the public paths within the same file (a public alias can point to a private container of the same file; other files are not expanded); it owns its names, paths, and docs, and is never evicted.
  - `FileLinks`: the namespace each declaration refers to, and the canonical targets of aliases.
  - `Exports`: the closure expanded along public members; each namespace keeps only one public path, the one with the fewest hops, which terminates alias cycles; names and docs reference the values of `FileDecls` directly and are compared for equality by pointer. Each namespace used by completion (the roots of the modules, and the namespaces that the aliases of the current file point to) has its own closure; at most 1024 values and 16 MB are kept, and evicted ones are expanded again from `FileDecls` and `FileLinks`; the dependency metadata the engine keeps for each key does not count toward this limit.
- Only `.zig` files are indexed, and auto-import is offered only in `.zig` documents: a module root can be a data file (such as JSON added by `addAnonymousImport`), and inserting an import declaration into a `.zon` or similar file would break it. When `completion.auto_import` is off, no index is built; a round already in progress stops before the next batch, and the values already built are kept until the end of the session.
- Indexing starts only on the first completion at a name that can be auto-imported, so sessions without completion (browsing, goto) do not pay for this memory and computation. Background indexing has two steps: first the workspace symbol index of the project files, usable as soon as it is built; then the auto-import index: the public closures of the standard library, `builtin`, and each named module are indexed in batches along the files involved (evicting intermediate results such as parse trees between batches), then the `FileLinks` and `ImportSites` of the project files, and finally `TestOnlyFiles` is computed (reading only the `ImportSites` already computed for each file, without parsing all project files in one read transaction); the index is marked usable only when all of this is built. The namespace and alias target of each declaration are cached per declaration (`DeclNamespace`, `DeclTarget`, keyed by the declaration's AstId): large standard library files have over a thousand declarations, so when an edit interrupts the indexing read transaction, declarations already computed need not be recomputed, and the index can still be completed during continuous typing; declarations unchanged by an edit also hit the cache directly. When evaluating a single declaration takes longer than the interval between two keystrokes (such as when the condition of `pub const X = if (slow()) A else B;` runs many comptime loops), an interruption means starting it over, so the index cannot be completed during continuous typing and is completed once typing stops. Until the index has been built for the composition of the current module graph (the standard library, the roots and builtin of the modules, and the import tables of the modules), completion offers no auto-imports and is marked incomplete (the client requests again as the user types), and closures are not expanded synchronously within the request; a module graph that only gained or lost files (generated files produced by the build, newly imported files) does not affect this, and the syntax indexes of those files are built on demand during completion. When the previous round did not finish (an error, or the task failed to start) and no indexing is in progress, the next such completion starts it again. The indexing task may run inline while completion holds a read transaction; when it runs inline, its read transaction and a waiting write transaction would wait for each other, so it is scheduled from another task.
- `BindingNames` depends on the current file's syntax tree independently, collecting only declaration sites (ItemTree members, parameters, local variables, captures) and never treating plain name references, member accesses, or labels as declarations; adding or removing a binding inside a function body updates the conflict check without widening the invalidation of `FileDecls` to function bodies.

Constraints on semantic tokens:

- **Classification**: types, namespaces, variables, functions, methods, and members are distinguished by their actual types and bindings, not guessed from names. The abstract classification of a declaration is cached separately; declarations of and references to type aliases are refined by the instance at the current position, without writing back across instances. Quoted identifiers follow lexical scoping; bare builtin names and `_` keep their language semantics.
- **Error tolerance**: each member's candidate instances and the per-iteration results of loops are reused, and at each token position an instance under which the token resolves is chosen. The search is bounded: a token that cannot be resolved keeps its syntactic highlighting, and functions are not guessed from call syntax. Inference under an instance happens only at positions whose classification may vary between instances: references to declarations classified as variables or types, local bindings (except type parameters), and member accesses where abstract inference cannot find the member; functions, methods, namespaces, and type parameters are classified the same under every instance, so no call sites are looked up for them.
- **Unused bindings**: lexical references are counted by binding identity, and `unused` is added only to parameters of functions with a body, local variables, and captures. Writes, asm outputs, and explicit discards count as uses; top-level declarations and container members are not judged from local references. This changes only the highlighting and produces no diagnostic; Neovim uses the theme's dimmed `DiagnosticUnnecessary` color for it.
- **Partial mode** (`semantic_tokens.mode = .partial`): tokens whose classification can be determined without name resolution or type inference (keywords, comments, literals, operators, labels, and builtin names with `defaultLibrary` such as `@import`, `u32`, and `true`) are not sent and are left to the editor's syntax highlighting. Tokens are filtered by their classification results; the analysis is the same as in full mode, and every token sent is identical to the same token in full mode. Full, delta, and range requests all follow the current configuration, and the client is asked to refresh when the configuration changes.
- **Global variables** (`semantic_tokens.global_var`): declarations of and references to container-level `var`s (names, member accesses, references in other files) are marked `global`; container-level consts, fields, and local variables are not. The new modifier is appended to the end of the legend, and the indices of existing token types and modifiers do not change.
- **Encoding and ranges**: tokens use the negotiated position encoding and are emitted sorted, single-line, and non-overlapping. An empty range returns immediately; otherwise the CST and the owner analysis are clipped to the range, while lexical references outside the range that affect `unused` are still kept. Whole tokens that intersect the range are returned, with positions relative to the start of the document.
- **Incremental updates and caching**: full, delta, and range requests are supported. A delta computes the common prefix and suffix in whole tokens and is expressed as one replacement of the part between them; it returns empty edits when nothing changed, and the full result when the baseline is unavailable. Only the latest snapshot of each open document is cached, for at most 128 documents and 16 MiB; closing a document frees its snapshot, reopening it isolates the old session, and range requests do not modify the snapshot.
- **Refresh**: when the client supports refresh, changes to semantic dependencies trigger a coalesced refresh request. After a refresh is sent, earlier results no longer serve as delta baselines, and the next delta request of each document returns the full result.

Constraints on inlay hints:

- **Local variable types** (`inlay_hints.types`): local variables without a type annotation show their inferred type; when the type cannot be inferred inside a generic function body, the instance from a call site is used, and the tooltip names the call it is based on. Constants whose value is a type get no hint.
- **Field types** (`inlay_hints.field_types`): in initializers (`T{ ... }`, `.{ ... }`), the type of each field is shown after the field name. The initializer's type is the same as in inference: the written type, or the result type with error union and optional stripped (the type recorded for the expression has already been converted to the result type and cannot be used directly); generic containers use the types in the instance. Anonymous initializers without a result type get no hints: their field types are just the types of the values.
- **Anonymous containers** (`inlay_hints.anonymous_containers`, off by default): when a type contains an anonymous container displayed by its contents, neither local variable type hints nor field type hints are shown; turning the option on shows them. Hover and completion details are unaffected and always show such types.
- **Parameter names** (`inlay_hints.parameters`): ordinary calls take the parameter names from the function declaration, and method calls skip the receiver; calls through a value of function type (function pointers, vtable fields, callback parameters and captures) take them from the `fn (...)` type expression the value's declaration is typed with (through pointers, optionals, and type aliases), or from the function declaration it is initialized with (`const f = &add;`), the same as signature help. For builtins (`inlay_hints.builtin_parameters`; also hidden when `parameters` is off), parameter names come from the parameters in the official documentation, with the `comptime` / `noalias` prefixes removed. Whether a multi-parameter builtin shows them is decided by a table in `inlay_hints.zig` that covers every multi-parameter builtin: they are shown only when the names add information the arguments do not reveal (arguments of the same type in an unconventional order, configuration passed by position to type constructors, an unusual parameter order), and a newly added multi-parameter builtin is a compile error until the table decides it. Single-parameter builtins all show names, subject to the single-argument rule; variadic builtins and builtins without parameters have no names to show.
- **Single-argument calls** (`inlay_hints.exclude_single_argument`, on by default): calls with only one argument show no parameter names, counting the arguments as written: a method call left with one argument after the receiver is removed counts too. This also applies to builtins.
- **Redundant parameter names** (`inlay_hints.hide_redundant_param_names`, on by default): no name is shown when the argument, after stripping wrappers that do not change the value it refers to (`&x`, `x.*`, `x.?`, `try x`, possibly nested), is a variable with the same name as the parameter, or a field access whose last segment has the parameter's name. This is decided on the HIR rather than by comparing the last token of the argument: `a + x`, `-%x`, and `x orelse y` produce new values and are annotated as usual. This also applies to builtins.
- **Refresh**: when any of these options changes, a refresh is requested (`workspace/inlayHint/refresh`) if the client supports it; like the semantic tokens refresh, it is also requested (coalesced until the client responds) after changes the client cannot see: another document edited, opened or closed, files changed on disk, and the standard library or module graph loaded.

Type display (hover, inlay hints, and completion details share `render.zig`): a container that is the value of a member is named after the member: `const S = struct {...}` is `S`; in a function body it is named after the local constant; a `return`ed container is named after the function and its comptime arguments (`List(u8)`); only that returned type carries the arguments, and a container named inside a generic instance is qualified by the named container or function, as the compiler names it (`Outer(u8).Inner`, `Outer(u8).Gen(u16)`, and `List.S` for a local constant of a generic function, without the arguments); when the value is an `if` / `switch` choosing among several containers, it is likewise named after the member (the compiler names it `S__struct_1` here; naming it after the member is more readable). Containers in type annotations of fields and variables, in arguments, in `?struct {...}`, and the like have no name in the source and are displayed by their contents: `packed struct { x: u8 }` and `union(enum) { a: u32, b: void }` list the fields and their types (enums list only the names); anonymous containers nested inside them are expanded the same way, and a self-reference (`?*const @This()`) is displayed as `struct {...}`, so the expansion is never infinite.

Value display: a declaration is displayed as `const x: T = v`, with the comptime-known value written after the type; at a reference, `T` is the type of the reference itself, not the type its result type coerces it to (`a: u8` passed to a `?u8` parameter is shown as `u8`). The type of a tuple or anonymous struct whose fields are all comptime fields is fully determined by its value (the type of `.{ A, B }` is `struct { comptime type = A, comptime type = B }`, the same as in the compiler), so only the value is shown: `const qs = .{ A, B }`. Hover and completion details list the full contents of types, without truncation (`@typeName` instead gives the compiler's fully qualified name, such as `main.S.Inner` or `array_list.Aligned(u8,null)`, and has no value when that name cannot be determined exactly, e.g. for containers the compiler names after a global counter); a value in hover and completion details is cut at about 2000 characters (`render.max_value_length`), and the cut is marked by `…` followed by the full number of items or bytes (`.{ 7, 7, … (3000 total) }`, `"ab…" (1048576 bytes total)`). A value that is directly the result of `@embedFile` (a constant initialized with the call, also with a type annotation the content coerces to such as `[]const u8`; a variable initialized with it whose value is known at comptime; the call expression itself) is shown as the call instead of its bytes, with the type unchanged: `const blob: *const [1048576:0]u8 = @embedFile("blob.bin")`, at the declaration, at references and in completion details. Hover adds the file the path resolves to, relative to the workspace folder containing it (otherwise absolute), and its size (``Embedded file `assets/blob.bin`: 1048576 bytes``); when the content is text (valid UTF-8 without control characters other than tab, line feed and carriage return) of at most `render.max_value_length` characters, the text follows in a `text` fenced block whose fence is longer than any run of backticks in it. Values computed from the content (a slice, a concatenation) keep the cut display. Inlay hints are shown inline, with nested anonymous containers displayed as `struct {...}`; a type hint is at most about `inlay_hints.max_length` characters (25 by default, 0 for no limit, the same as rust-analyzer's `inlayHints.maxLength`): if the output is already full before the next item of a list (fields, elements, arguments, parameters) is written, `…` is written and output stops, so a hint may exceed the limit by one item; strings are written only up to the limit.

Organize imports (`source.organizeImports`, `ide_db/organize_imports.zig`):

- **Blocks**: consecutive top-level import declarations (`const x = @import("...")`, optionally followed by member accesses) and derived declarations (whose right-hand side is a member access, possibly several levels deep, starting with an import or derived declaration of the same file) form a block, with only blank lines between declarations; comments directly above a declaration and its trailing comment move with it, except comment lines that start the file (a header such as a license notice), which stay first. A comment separated by a blank line, or any other declaration, ends a block; each declaration must occupy whole lines by itself. A file can have several blocks, each organized in place; declarations are neither moved between blocks nor removed (unused ones are diagnosed by the compiler). Nothing is organized when there are syntax errors.
- **Grouping and sorting**: three groups, `std` / `builtin` / `root` (in this fixed order), dependency modules, and files, with a blank line between groups; grouping looks only at the `@import` string (strings ending in `.zig` / `.zon` are files). By default a derived declaration directly follows the declaration it depends on (`imports.derived = .with_import`), or derived declarations form a separate last group (`.separate`); a derived declaration whose dependency is in another block always goes in the last group. Within a group, entries are sorted by default by what they reference (`imports.sort = .path`): module names, file paths (fewer `../` first, then compared segment by segment), and for derived declarations the access path expanded up to the name of the import declaration; `.name` sorts by declaration name. Comparisons use rustfmt's version sort (numbers by numeric value, uppercase before lowercase, `_` before every other character), consistent with rust-analyzer. These two options are a style shared by the team and can be set in `zig-analyzer.zon`.
- **When offered**: always offered when the client requests this kind in `context.only` (`source` included), which is used for keybindings and organizing on save; for menu requests (no `only`), it is offered only when the requested range intersects a block. Applying it organizes all blocks; it is not offered when the imports are already organized, and organizing the result again changes nothing. Other code actions are filtered by `only` as well.

Removing unused parameters (`ide/remove_param.zig`):

- **Offering**: when AstGen reports `unused function parameter`, the code action "remove parameter `x`" is offered besides the discard (`_ = x;`, preferred), and it is not marked as preferred. The function must have a body and be in the user's code (as with rename); the action is not offered for `export` / `extern` functions, variadic functions, or the receivers of methods: the first parameter is a receiver when its type is the container the function is in or a single-item pointer to it; the type expression is first resolved by name (`@This()`, `Self`), and when that fails (the result of a type function), the inferred signature is used. When the client supports `codeAction/resolve`, call sites are searched only after the action is selected; otherwise the edit is computed in the request, and when the parameter cannot be removed, the reason is given in `disabled`; when the client does not support `disabled`, the action is not offered.
- **Call sites**: references are searched in the same scope as for rename. Every reference must be the callee of a call (possibly parenthesized): `f(...)`, `S.f(...)`, `x.f(...)`, or the decl literal `.f(...)`; the names of decltests do not depend on the signature and are left unchanged. In `x.f(...)`, when `x` is a value, it is a method call and `x` is the first argument; when `x` is a type or a namespace, it is not. In a generic function, this is decided under all call-site instances, which must agree. The number of arguments (counting `x` in a method call) must equal the number of parameters.
- **Refusal**: in the following cases no edit is returned, only the reason and the location: the function is used other than in a call (passed as a value, its address taken, `@call`, `@TypeOf`); a reference is ambiguous in a generic function, goes through a member access of unknown type, or appears in a file with syntax errors; the function name appears as a string literal in a file that can access the function (for a `pub` function, the files that import the file containing it; otherwise, the file containing it), so it may be accessed by name through `@field` and the like; a method call passes the value before `.` as the parameter being removed; a removed argument has side effects: calls (except type function calls whose result is a type), assignments, `try` and control flow, builtins that have side effects or are not listed, inline assembly, and so on. If any one place cannot be updated, the whole fix is refused, with no partial edits.
- **Validation**: for each modified file, the AstGen errors before and after the edit are compared (matched by position and message), and the fix is refused when new errors appear, for example when removing an argument leaves a local constant at a call site or a parameter of the caller unused. The exception is another parameter in the same parameter list that becomes unused as a result (after `x` is removed from `comptime T: type, x: T`, `T` is unused): it is equivalent to the original error and can be removed next. When a removed argument contains a call to the same function (the type function `Wrap(Wrap(u8, u16), u32)`), the edit of the inner call is dropped along with the argument.
- **Layout**: an item on lines of its own (an item of a multiline list, together with its doc comment and trailing comment) is removed with those lines; an item that shares a line with other items is removed together with one comma (for the last item, the comma before it); next to a multiline string literal, the removal stops at the comma, keeping the line breaks before and after the multiline string; a `//` comment after the separator before the item (`(` or the previous comma) on the same line belongs to the previous item or to the call and is kept with its line break (for the last item, `)` then goes on the next line with the indentation of the line of `(`); when only whitespace remains between the parentheses after the removal, the parentheses are emptied, giving `f()`.
- **Limits**: for `pub` functions, only calls in the workspace are updated, not callers outside the workspace; when the client supports `documentChanges` and change annotations, the edit carries an annotation that needs confirmation and is applied only after the user confirms.

Unused captures (`ide/unused_capture.zig`):

- **Offering**: when AstGen reports `unused capture` or `unused switch tag capture`, the code action "remove capture `v`" is offered, or "rename `v` to `_`" where the capture cannot be removed. Only rewrites that keep the meaning are offered: which captures can be removed or renamed to `_` follows the rules of AstGen, and the fix is not offered when no such rewrite exists. When the body of the capture is a block, the fix is offered besides the discard (`_ = v;`, preferred) and is not marked as preferred; otherwise no discard can be inserted and the fix is preferred, except renaming the payload capture of a switch prong whose tag capture is unused too: the preferred fix of the tag removes it, and applying both would leave `|_|`.
- **Removing**: an optional `if` / `while` (without `else |err|`) loses the capture, and its condition is compared with null (`if (x) |v|` → `if (x != null)`), wrapped in parentheses unless it is a suffix or primary expression (`if ((a orelse b) != null)`); `catch |err|` loses the capture (`catch |_|` is an error); a switch prong with only the payload capture loses the whole capture, and a tag capture is removed together with its comma, or the whole capture when the payload capture is `_` (`|_|` and `|p, _|` are errors); an unbounded for counter (`0..`; discarding it is an error) is removed together with its input. The start of that input must be a literal, a name, or a field access on a name, and a bounded input must remain; when the start contains a name, AstGen is run on the rewritten text and the fix is not offered if new errors appear, matched by position and message (a name used only there is no longer used, which may be another `unused capture`).
- **Renaming to `_`**: both captures of an error union `if` / `while` (removing the payload capture requires a void payload, and removing `else |err|` turns it into an optional `if`), the other captures of a for, and the payload capture of a switch prong that also has a tag capture; a pointer capture is renamed together with its `*` (`|*_|` is an error).
- **Layout**: a removed capture is deleted together with the whitespace before it, or the whitespace after it when it starts a line; a removed for input is laid out as when removing parameters.

Naming checks (the Names section of the Zig 0.17.0 style guide; enabled by `naming.enable`):

- **Classification**: the style of a name is decided by what the declaration actually represents, not by the `fn` / `const` / `var` keyword: types, type aliases, and callables that return `type` are TitleCase; other callables (functions, function aliases, function pointers) are camelCase; files without top-level fields (namespaces) and other values are snake_case; fields and enum members follow the type of the field. Acronyms are treated as ordinary words (`XMLParser` → `XmlParser`). Only inference results of the abstract instance are used; a conclusion drawn from the instance at one call site is not generalized into a rule for the source.
- **Skipped**: types that are unknown or depend on the generic instance; structs without fields (whether one is a namespace or a zero-size type to be instantiated depends on intent); fields holding types, and optional function pointers (the standard library uses both styles); extern / export declarations and extern containers; `@compileError` stubs (`noreturn`: they keep the name of the API they replace, so that its users get their message); top-level declarations whose names the standard library looks up in the root file (`DllMain`, `WinMain`, `std_options_cwd`, and the like; checked in every file); aliases re-exported under the same name (`const SDL_Window = c.SDL_Window;`, where the name is determined by the referenced declaration); names written as `@"..."`; names whose word split is ambiguous (no lowercase letters as in `ENOENT`, a `_` prefix or suffix, words of fewer than five letters split off from a run of uppercase letters as in `URLs` / `CIELChuv`, a single uppercase letter after a digit as in `Vec3D`). Files in dependency libraries, generated code (whose leading comment carries a marker such as `DO NOT EDIT` or `@generated`), and files in `naming.exclude` are not checked.
- **Hints**: published only for open files, with severity Hint, code `naming.<rule>`, and a link to the official rule; `naming.ignore` (names, with `*` wildcards) and `naming.rules` set exceptions, and these options can also be written in the project's `zig-analyzer.zon`. Results are cached per member (`naming.Query`, without positions or configuration); an edit recomputes only the changed members, scans no other files, and starts no compiler process.
- **Fixes**: a code action "rename ... to ...", not marked as preferred and applied only after the user selects it; when the client supports `codeAction/resolve`, references are searched only after it is selected. In the following cases no edit is returned, only the reason: a reference is ambiguous in a generic function, goes through a member access of unknown type, or appears in a file with syntax errors; the new name duplicates a member of the same container, shadows or is shadowed, or makes a reference in the container ambiguous (a declaration in an inner container may share its name with one in an outer container, and Zig reports only the references that see both, as `ambiguous reference`); the name appears as a string literal (`@field`, `@hasDecl`, serialization keys). Finally, AstGen is run on the renamed text of the file containing the declaration, and the rename is likewise refused if new errors appear: duplicate names and shadowing can only occur in this file, and references in it that were missed are reported as well.
- **Limits**: for public names (`pub` declarations and fields), only references in the workspace are updated; users outside the workspace, symbols of external ABIs, and string names constructed at runtime or passed through variables (such as JSON serialization keyed by field names) are not. When the client supports `documentChanges` and change annotations, such renames carry an annotation that needs confirmation and are applied only after the user confirms.

### 4.7 Build integration (`project/`)

- Acts directly as a client of the official build system protocol `zig build --listen=-`: the handshake checks `build_system_version`; the build graph (`std.Build.Configuration`) in `bsp_configuration` is read and converted into a ProjectModel; builds are requested per step, and the `ErrorBundle` and generated file paths are taken from `bsp_step_completed`; `bsp_configuration_failed` is published as diagnostics of `build.zig`. A diagnostics step or one of its dependencies that fails without reporting errors, and not because one of its own dependencies failed (a missing system library, a failing Run or Fail step: the cause is only on the maker's stderr), is named in the end of the build progress instead of `Done`, and the user is warned once until the set of such steps changes.
- The build graph contains only modules reachable from steps. A project without any compile step (a library that only exports modules and is compiled by its users) gets a probe package generated in `.zig-cache/zig-analyzer/exports`: it has the project as a path dependency, adds an object step for each exported module, and reuses the project's `zig-pkg`. The modules and compile steps read from it are merged into the ProjectModel, used only to determine module membership, and never appear in build requests.
- C bindings are generated by the build system's translate-c (Zig 0.17 removed `@cImport`) as modules rooted at generated files, whose paths become known after the build.
- As the paths of generated module root files become known one by one during a build, the compile set is recomputed and the module graph updated without waiting for the whole build to finish, but throttled: at least 1 second after the previous recompute ends, and no less than 4 times its duration. Reading build events and recomputing happen in the same task, and on a large project one recompute can take seconds (the Zig compiler's build graph has over four thousand compile steps); with a fixed interval, this task would recompute all the time, the maker's events would pile up, the build would slow down, and the module graph would update every second throughout the build.
- Generated file paths that the maker reports with the `local_cache` prefix, and paths in the build graph relative to the local cache, are resolved against the local cache directory the maker actually uses. It is derived from the path of the build graph given in `bsp_configuration` (`<local cache>/c/<hash>`, or `tmp/<hex>` when no cache is used), so `--cache-dir` in `build.args` and `ZIG_LOCAL_CACHE_DIR` are respected. Rename does not modify generated files in this directory; when the local cache directory contains the build root, generated files and project files cannot be told apart, so the directory is not used for exclusion.
- Among the dependency packages containing modules, those whose root directory name is the package hash are fetched packages (the maker stores fetched packages in the `<hash>` subdirectory of the package directory); their root directories are recorded in the ProjectModel to tell dependency code apart from user code. A package given by `--fork` uses the directory the user specifies and is not included.
- The same process provides both the project model and the compiler diagnostics. A restart runs as a new instance:
  - First the maker and its child processes are ended, for both the project's current instance and any new instance that has not replaced it yet; then the new instance is started. The new instance replaces the old one when its first build completes (or configuration fails while the old instance has no model, or no build is needed); until then, the old instance's model, compile set, and compiler diagnostics stay in effect, and build requests are forwarded to the new instance. When the old instance has no model and compile set, the new instance replaces it as soon as it has computed its compile set. When configuration fails while the old instance has a model, the new instance is dropped instead: the old instance's model and compile set stay in effect (named imports keep resolving, and references and rename keep finding importers), and the configuration errors replace its compiler diagnostics until `build.zig` is saved again. Instances are reclaimed by reference counting.
  - Restart triggers: `build.zig`, `build.zig.zon`, or `zig-analyzer.zon` in the root directory, or a build script (a file reachable through `@import`s along relative paths from the `build.zig` of the project or of a dependency package with a `build.zig`, found through the `.dependencies` of each `build.zig.zon` (`.path` relative to the declaring package, `.hash` in the package directory), together with those packages' `build.zig.zon`: the maker compiles all of them into the configure program), is saved or changes on disk; a configure input that `build.zig` declares (`b.dependOnFileContents`, `dependOnFileMetadata`, `dependOnDirectoryContents`, ...; the build graph's `path_deps`) changes: such a file is saved, created, deleted, or changed on disk, or such a directory is created or deleted or an entry is created in or deleted from it (not recursive), as `zig build` repeats the configure phase then; the build configuration changes; the maker crashes (restarted immediately, at most 3 times in a row without a completed build in between: the crashes it recovers from are races in the maker, which waiting does not avoid); the maker's local cache directory or its `h` directory is deleted or replaced (the maker writes through the handles it opened at startup, so steps writing into the cache would fail without errors; checked by inode before each build and when a build ends, and a build that ends this way keeps the previous diagnostics). Creating or deleting `build.zig` in a root directory starts or stops the project.
  - When the new instance is abandoned (the maker crashes more times in a row than the limit, exits during the configure phase without sending configuration errors, or the protocol version does not match), the old instance's compiler diagnostics are cleared and its model is kept until `build.zig` is saved again. A maker that exits before sending a build graph or `bsp_configuration_failed` failed its configure phase (an invalid option in `build.args`, an unknown target, an error or panic in `build()`): this is not a crash and is not restarted, since it would fail the same way; the user is shown the line of its stderr that gives the cause (the maker's stderr is always read, keeping its last 64 KiB). When the build graph cannot be read, the user is notified and the maker is stopped until `build.zig` is saved; when `bsp_configuration_failed` contains no errors (a problem with `build.zig.zon` or a dependency package, which the maker writes only to its stderr), the located errors on its stderr (`<path>:<line>:<column>: error: ...` with their source line, marker line, and notes) become the configuration errors, published on `build.zig.zon` like the errors of `build.zig`; when none can be located, the user is shown the line of its stderr that gives the cause.
- Process management: the maker and the child processes it starts belong to a process group led by a watchdog `sh` on POSIX, and to a Job Object with `KILL_ON_JOB_CLOSE` set on Windows. Stopping a project (shutdown, exit, end of input, restart) ends the whole group immediately, without waiting for the build; however the server exits, the whole group ends with it. A maker ended this way never runs its clean exit, which is where it deletes a poisoned build graph (one that cannot be cached, e.g. when `build.zig` calls `b.findProgram`, left in `<local cache>/tmp` for a single run): the server deletes such a build graph once it has read it, or when the instance that received it is stopping.
  - Each single-file `zig build-obj` and the processes it starts form such a group as well. Shutdown, exit, end of input, and the exit of the client process end the compiles in progress immediately, without waiting for them or publishing their results, and start no further compiles (including those requested during a compile); however the server exits, the compilers end with it.
- zig environment: at startup, `zig env` is run to get the lib directory, the standard library directory, and the global cache directory. When it cannot be run (zig not found at `zig.path` or in `PATH`, or `zig env` fails), the user is warned: without it there is no standard library, no named modules, and no compiler diagnostics.
  - `zig.lib_path` and `zig.global_cache_path` override the detected directories: the lib directory must contain `std/std.zig`, and the cache directory must already exist; otherwise the user is notified and the detected directory is kept. The overriding paths are passed through the environment variables `ZIG_LIB_DIR` and `ZIG_GLOBAL_CACHE_DIR` to every zig process that is started (`zig build` has no argument for setting the global cache directory), so the maker, single-file compilation, and the generation of builtin.zig use the same standard library as name resolution.
  - `zig.builtin_path` replaces `@import("builtin")` for files that belong to no project (by default it is generated for the native target with the settings of `zig build-obj`, as single files are compiled); modules in projects still use the one generated from their build arguments, so their own targets are unaffected.
  - When these options change, they are applied again: the standard library and builtin.zig are reloaded with the module graph; when the lib or cache directory changes, projects restart and detached files are recompiled. A replaced environment is freed only when the server exits: tasks in progress and running project instances may still be using it.
- Version coupling: the `Configuration` format and the in-process AstGen both come from the standard library zig-analyzer is compiled with. The build graph file has no version number and is read as raw structs, byte for byte, so a mismatched format is misread (the `build_system_version` checked in the handshake covers only the protocol messages). It is therefore read only when the user's zig version is exactly the one zig-analyzer was compiled with. Before it is converted, the lengths in its header must add up to the file size and every index, tag, and string the conversion follows must be in range; a file that fails this is reported like any other unreadable build graph.
  - When the versions differ, the build system is not started for root directories with `build.zig`: there are no compiler diagnostics, imports of named modules (dependency packages, build options) cannot be resolved, and only the live diagnostics of `zig ast-check` remain. Files under these root directories are not compiled in single-file mode either (files that use named modules would report modules not found). At startup, the user is told both versions and the affected features.
  - Other files are still compiled in single-file mode, reading the `ErrorBundle` produced by the user's zig. Its format has no version number either: it is validated as described in §3 before use and dropped if validation fails; a bundle that passes validation is never read out of bounds, but with a mismatched format the diagnostic contents may be garbled.
  - Release versions follow Zig versions. The version a binary reports (`--version`, `serverInfo`) comes from `git describe --tags` at build time, and falls back to the version in `build.zig.zon` when no tag is reachable or git is unavailable. Since git's answer is outside what the configure cache tracks, `build.zig` marks its configuration as not cacheable, so every `zig build` runs the configure phase.

### 4.8 Server and concurrency (`server/`)

- Write messages (document sync, configuration, workspace and file-watching events) run serially: register as waiting (increment the cancellation counter) → wait for readers to exit → apply the changes and advance the revision. The main loop's message handling and the handling of external changes discovered by the server are serialized by the same lock.
  - No write transaction is opened when the inputs have not changed: a write of an identical value does not advance the revision, but it still cancels in-flight read requests (answered with `ContentModified`) and background computations. The module graph is recomputed after every build; when it is the same as the current one, the update returns immediately.
- Requests that use name resolution and types are answered at once while the zig environment or a project's first load is pending, on what is known so far. A hover then says that the project is still loading; other answers have no place for such a note and may lack results. With `sema.wait_for_project`, these requests are held back until the load ends (or they are canceled, or the server shuts down) and every answer is complete; what changes meanwhile cancels a held request only when it changes the text of the request's own document (`ContentModified`), since its positions refer to that text. While the configuration that starts the projects is on its way from the client, whether that setting is on is not known: these requests are held until it arrives in either case. A restart (`build.zig` saved, settings changed) does not end a first load: it goes on in the new instance. Syntax features never wait.
- Read requests run concurrently on snapshots; both `$/cancelRequest` and write transactions can cancel them. A request is answered on the state at the time it was received: when its task starts reading only after a write transaction that began since then (such as a later `didChange` applied by the main loop), it is answered with `ContentModified`. The server's own updates (the module graph, the workspace file list, the live diagnostics backend) are not ordered with the requests: a request that starts reading after one has finished reads its changes.
  - Requests whose results depend only on document text (formatting, document symbols, folding ranges, selection ranges, the syntax tree) are canceled only by writes that may change text: the server's own writes of the module graph, the workspace file list, and the live diagnostics backend wait for them instead.
- Diagnostic publishing: edit-triggered publishing is debounced per file and given up when superseded by a newer edit; live diagnostics (in-process AstGen and the `zig ast-check` child process) are computed outside read transactions and do not block write transactions. While a compile is in progress, the previous round's results are kept; when it completes, they are replaced atomically. Compile results never change after creation and are shared by reference counting: a publish takes a reference under the owner's lock and releases the lock right away, so a result is not freed during merging even if it is replaced, and it does not need to be copied.
  - The publish queue coalesces by file: a file already in the queue is not enqueued again (requests to clear old diagnostics are combined as a union), and a file being computed is published once more after it finishes. Every state change (such as a build finishing) requests publishing for the open files, and computing the same file concurrently is just duplicate work.
  - The diagnostics of a file may depend on the text of other files (notes and reference traces located in them, inactive code whose conditions read them, naming hints that depend on their declarations). So when a document is edited (after the debounce), opened or closed, or a file changes on disk, the other open files are recomputed too; such a result is sent only when it differs from the last one sent for that file.
  - Edit-triggered publishes bypass the queue and may compute concurrently with queued ones: each takes an increasing sequence number before reading state, and only results whose number is no smaller than the one already sent are sent. Every state change is followed by a publish, so the last result sent has read the state after the last change.
- Configuration comes from the client (`initializationOptions`, `workspace/configuration`); a `zig-analyzer.zon` in the project root (ZON, comments allowed) can override the project-related options. See `src/server/Config.zig` for a description of each option. Settings pulled through `workspace/configuration` or pushed through `workspace/didChangeConfiguration` replace the current settings; a `null` section in the reply to a pull means the client cannot provide it, and the current settings (from `initializationOptions` or an earlier push) stay in effect.
- Exit: on `exit` and at end of input, the read requests in flight are canceled instead of awaited (nobody reads their results anymore; `shutdown` still waits for them), and the server no longer waits for the client's replies to configuration requests (a `zig-analyzer/waitIdle` request in flight waits for them); it stops all projects and exits. When `initialize` gives a `processId`, the server waits for the client process to exit and then exits too (the write end of stdin may be inherited by other child processes of the client and never be closed). The wait uses the operating system's process exit notification: a pidfd on Linux (since kernel 5.3), kqueue's `EVFILT_PROC` on macOS, FreeBSD, NetBSD, and OpenBSD, and the process handle on Windows. Only when none of these is available (old kernel, forbidden by a sandbox, no permission to open the process, other platforms) does it check every 2 seconds whether the process still exists.
- External changes: when the client supports dynamic registration, the server registers `workspace/didChangeWatchedFiles` (`.zig` and `.zon`; other files read by `@embedFile` and the files among the configure inputs are additionally registered by file name, as `**/<file name>`, once interned, the directories under the root directories that contain interned files by their name, as `**/<name>`, and the configure input directories as `**/<name>` and `**/<name>/*`). Clients report a folder created, deleted, moved or renamed by its own path only: an event for a path that is not a known file applies to every known file under it. When the client does not support it (the default for Neovim on Linux), or when `files.watcher` is `server`, the server watches the files itself; with `auto` and a client that registers the watchers, the server still watches the files outside the root directories itself, since clients apply the registered watchers inside the workspace folders only (without workspace folders, that is every file); when the client answers the registration with an error, `auto` watches every file on the server as if the client did not support it. When the server starts watching files nobody watched before (`files.watcher` changed at runtime, or the registration rejected), it compares them with the disk once: a known file whose known text (for one only read from disk on demand, the contents that read) differs from the disk is handled as changed, the others trigger nothing; open documents are skipped. Changes are handled along the same path:
  - Files of interest are the interned files (`.zig` / `.zon`, files read by `@embedFile`, and the files among the configure inputs), the configure input directories, and `build.zig`, `build.zig.zon`, and `zig-analyzer.zon` in each root directory, excluding files in dependency libraries (§3); open documents are included: their buffers take precedence over the disk contents, but builds read the disk, so their changes on disk rebuild (or restart) like those of other files. The configure input directories are watched themselves as well (their modification time is polled when they cannot be watched), so entries created in or deleted from them are reported.
  - A change that leaves the contents the same is not a modification. When a build step rewrites a file in the source tree unchanged every time (such as generated code), treating that as a modification would rebuild, which rewrites the file again, so the server would never become idle. When a file changes several times in one batch, the last change wins (an atomic save first deletes and then recreates the file).
    - Whether to write and republish is decided against the known text: when it is the same, nothing is written or republished. For a file whose text was never set, the known text is what it was read from disk on demand (`SourceText`), if anything read it: a file nothing has read yet is not changed, since nothing was computed from its contents. FSEvents reports writes made shortly before the stream started, such as the files of a checkout made just before the editor starts; writing them would cancel the requests in flight.
    - Whether to rebuild (including restarting projects and recompiling single files) is decided against the disk contents read when the last rebuild was triggered this way or by saving the document (recorded as a hash): builds read the disk, whereas the known text may also come from reading the file when a document is opened or closed, or when it is first loaded, which a build has not necessarily seen. So the first time a file is rewritten unchanged, it still triggers one rebuild; after that, identical contents trigger none, and the notification of a save rebuilds nothing beyond the save itself. Opening a document clears its record. Without a record, `build.zig`, `build.zig.zon` and `zig-analyzer.zon` in a root directory are compared with their disk contents taken just before the project's newest instance started its maker, which reads them afterwards: a notification of those contents (such as one FSEvents reports for a write made before the stream started) does not restart the project.
  - The directories containing these files are watched with the operating system's native notifications: inotify on Linux, FSEvents on macOS, and directory change notifications on Windows. A directory that does not exist is watched through its nearest existing ancestor; once it appears, it is watched itself, and files already in it are treated as created. The directories to watch are recomputed when new files are interned (Vfs notification), roots are added or removed, directories are created or deleted, or notifications are lost. A name reported created or removed that has files of interest under it is such a directory, since Windows notifications do not tell directories apart (a rename or a move to the Recycle Bin): those files are checked again. A burst of notifications is merged into one batch (50 ms of quiet, delayed at most 500 ms). A notification that names a file of interest under another spelling (FSEvents reports decomposed Unicode names) counts for that file (§3).
  - Polling (checking size and modification time) is only the last resort: when native notifications are unavailable (other platforms, initialization failure), or some directories exceed the limit on the number of watches (such as inotify's `max_user_watches`), only the files in those directories are polled, at intervals of at least 1 second and no less than 20 times the duration of one check. A file's state is recorded when it starts being polled, like a watch being added, so a change before its first check is reported.
  - Handling the changes counts as busy: when a project restarts, whoever is waiting for idle does not return between the end of the old instance and the start of the new one.
  - Known limitation: on network file systems (NFS, SMB/CIFS, FUSE file systems such as sshfs), Windows-side files in WSL2 (`/mnt/c`), and directories shared with containers and virtual machines, native notifications do not report changes made on other machines or on the host, yet adding the watch succeeds, so there is no fallback to polling and these changes go unnoticed (as in rust-analyzer, the file system type is not detected).
- Client capabilities shape the results: `RenameOptions` only with `rename.prepareSupport`; code actions (which all carry edits) only with `codeActionLiteralSupport`, otherwise `codeActionProvider` is false; a `DocumentSymbol` tree only with `hierarchicalDocumentSymbolSupport`, otherwise a flat `SymbolInformation[]` naming the parent as `containerName`; symbol and completion kinds added after the initial protocol version only for clients that list their kinds (`valueSet`), otherwise the closest initial kind (`Struct` → `Class`, `EnumMember` → `Enum`, `Constant` → `Variable`); plain text instead of markdown (without code fences) when the client lists formats without markdown; signature help parameter labels as `[start, end]` offsets into the signature label (in the negotiated position encoding) with `labelOffsetSupport`, otherwise as substrings of it.
- Observability: slow request logging (`log.slow_request_ms`); `-Dtracy=<dir>` enables tracy. Custom requests (method names prefixed with `zig-analyzer/`; for the result fields, see the respective result types in `server/Server.zig`):
  - `status`: per-query execution counts, hit rates, time, and memory; InternPool and heap usage.
  - `fileStatus` (parameter `textDocument`): the file's origin (§3), its compile context (project, project directory, unloaded project, dependency library, detached file), whether it is open, the roots of its modules, the projects containing it and their last builds (completion time, file count, diagnostic count), and the roots of the single-file compiles rooted at it or containing it.
  - `syntaxTree` (parameter `textDocument`): the indented syntax tree (nodes and tokens) and syntax errors.
  - `moduleGraph`: the module graph combined from all projects: the standard library root, and each module's root file, builtin, imports, and file count.
  - `reloadWorkspace`: restarts all projects, the same as saving `build.zig`.
  - `waitIdle`: returns only once the server is idle (background tasks such as builds and diagnostic publishing have finished); used by tests and benchmarks.
- Crashes: Zig has no stack unwinding, so a panic ends the whole process. Before exiting, the message, the current thread's context, and the call stack are written to the log. The context includes the message the main loop is handling; the method, document, and position of a read request; the file whose diagnostics are being published; the root of a single-file compile; a project's build events; indexing; and the stack of queries being computed. Assumptions that analysis code makes about input data, where degrading is possible, use soft assertions (`util/assert.zig`): a failure panics in Debug and in tests; in other builds, each site logs only once and takes the degraded path.

## 5. Acceptance

### 5.1 Automated tests (CI, Linux / macOS / Windows)

| Command | What it covers |
|---|---|
| `zig build test-all` (Debug and ReleaseSafe) | All tests: engine (incrementality, cutoff, cycles, cancellation, eviction), syntax, names, sema, and IDE features, plus the build system protocol, single-file compilation, diagnostic consistency, and end-to-end tests, which run the zig in PATH |
| `zig build test --fuzz=<count>` | Coverage-guided fuzzing: URI ↔ path, parser losslessness, agreement between incremental and full parses, position conversion |
| `zig build corpus -- <dir or file>...` | Parser corpus cross-check (`.zig` and `.zon` files; `.zon` files are compared with the ZON mode of `std.zig.Ast`): lossless, no false errors, same structure as `std.zig.Ast`, no crash on truncation; HIR references correspond one to one to source positions and decoded names, including asm output targets, with nested containers checked by their own owners |
| `zig build check -Dtarget=x86_64-windows` (a Windows target whose minimum is Windows 10 1507, Zig's default) | Besides compiling everything, fails when the executable imports a function of ntdll, kernel32, or advapi32 that Windows 10 1507 lacks, per the version groups of the mingw-w64 `.def` files bundled with Zig; the loader would refuse to start it on earlier Windows 10 releases |
| `zig fmt --check`, no diff after `zig build gen` | Formatting and generated code |

- `zig build test`: runs only the tests that need no external tools, for quick checks during development. Under this step, zig is not found (`ZigEnv.query` returns `ZigNotFound` in this case), so the tests that depend on it (example projects, the real standard library) are skipped, and the server starts no projects or compiles.
- `zig build test-stress -Dstress-filter=<part of the full test name> [-Dstress-runs=<count>]`: runs the selected tests repeatedly, one after another, in server mode (50 times by default, each one actually run), to verify concurrency-related changes. A filter that matches no test fails.
- `zig build sema-corpus`: runs full type inference over the standard library, checking that nothing crashes and reporting the share of known types.
- When tests write logs to stderr, `zig build test` and `test-all` also print `failed command: ...`; exit code 0 means they passed. Real failures come with "N pass, M fail" and the test names.

### 5.2 Real-project benchmarks and cross-checks

```
zig build bench -Doptimize=ReleaseSafe -- <project root> <file (relative to the project root)>...
```

The benchmark starts the server as a child process and talks to it the way an editor does (like common editors, it declares `snippetSupport` for completion), measuring cold start (with `initialize` sampled over 5 server processes), hover / goto / completion latency, edit → diagnostics, continuous typing, warm semantic tokens (full, range, and delta), and memory. Environment variables enable the individual checks (see the header of `tools/lsp_bench.zig` for details).

The exit code is 1 when a check below fails its pass criterion or when the semantic token deltas do not add up to a full result; `BENCH_SESSION` has no automatic verdict. Missed latency targets do not affect the exit code, because they apply to the benchmark project and §2.3 lists the known gaps.

The answers to 20 hover, goto, and completion requests each, sent right after the first file is opened, are compared with the answers once the project is loaded, and the output counts those given before the first load ended as `same`, `incomplete` (null, or fewer completion labels), or `different`. This is reported without a verdict: name resolution is incomplete during loading (§4.8); with `sema.wait_for_project` no answer arrives before the load ends.

| Variable | Check | Pass criterion |
|---|---|---|
| `BENCH_CHECK=<n>` | Requests declaration for identifiers; the name at the target must equal the name at the request position; unresolved identifiers are counted by kind (primitive types, `len` / `ptr`, error names, `.` literals, member access, labels, names) | Mismatches = 0 |
| `BENCH_COMPLETE=<n>` | Completes each `a.b` in the source after the `.`; the list must contain `b` | Recall ≥ 95% |
| `BENCH_CONCURRENT=<n>` | Throughput: opens the n largest files of the project at once and requests their full semantic tokens without waiting for the answers, as an editor restoring n tabs does; reports the time until the last answer, the latency of each request, and the memory afterwards | Timing covers the opens and all the answers |
| `BENCH_REFS=<n>` | Find references and rename; references in a generic function body that point to a same-named declaration under another call site's instance are counted separately | Name mismatches, false positives, misses, and rename inconsistencies all 0 |
| `BENCH_SAVE=1` | Save → compiler diagnostics. Published errors are compared with the output of `zig build` for the same steps and the arguments in `BENCH_CONFIG`: file, message, the printed location within the published range, and notes. Reference traces are not compared, and a project with a `zig-analyzer.zon` is not compared, because it may set other arguments | Identical |
| `BENCH_SESSION=<rounds>` | Memory over a long session (`imp MB` is the value for the auto-import index; `small`, `resid`, `slots`, `kept`, `ret`, `large` and `dec k` are the allocator's figures from `zig-analyzer/status`, `occupancy %` the share of its pages by the eighth of their blocks in use, `thp` the memory in transparent huge pages on Linux, and `commit` the private commit on Windows), and the latencies of the session's requests | Stable, within budget |
| `BENCH_TYPE_COMPLETE=<n>` | Completion while typing: insert a character in a name expression → complete → undo, also reporting the number of auto-import candidates and the changes in index queries (auto-import is on by default; disable it with `BENCH_CONFIG='{"completion":{"auto_import":false}}'` to compare the cost) | Timing includes the edit and the completion |
| `BENCH_TYPE_WORDS=<line>:<word>,<word>...` | Types each word character by character in a new statement after line `<line>`, requesting completion after each character; waits for background work to finish before each keystroke, so the timing covers only that edit and completion; also reports the number of candidates and how many of them are member paths of local values | Timing includes the edit and the completion |
| `BENCH_TYPE_STMT=<statement>` | The statement `BENCH_TYPE_WORDS` inserts, with `\|` marking where to type (default `_ = \|;`); e.g. `const probe: Air.Inst.Ref = \|;` types where there is an expected type | — |
| `BENCH_QUICK=1` | Skips the edit-related phases; used for batch validation | — |

In addition, `textDocument/formatting` is cross-checked against `zig fmt` (identical character for character).

Batch validation: for each library, the dependencies are first fetched with `zig build --fetch`; then the benchmark runs with `BENCH_QUICK=1 BENCH_CHECK=40 BENCH_COMPLETE=40 BENCH_REFS=20` on the one file in the root project (excluding subdirectories with their own `build.zig`, tests, and examples) that has the most member accesses. See `docs/test-list.md` for the projects, commits, and measured files.
